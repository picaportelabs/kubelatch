# Proxy de impersonación delante del Kubernetes API server (estado a 24 de septiembre de 2026)

Notas de ingeniería sobre el patrón "identity-aware reverse proxy + impersonation": el proxy autentica al desarrollador con credenciales emitidas por la app, y reenvía la petición al API server real con una credencial privilegiada por cluster y cabeceras `Impersonate-*`. Se cubren protocolo, pitfalls, rendimiento/HA, acceso a clusters privados y cómo lo resuelven las implementaciones open-source y comerciales existentes, para decidir entre "proxyar todas las peticiones" y "entregar credenciales nativas del cluster". Entorno objetivo: mixto (EKS/GKE/AKS + self-managed) y equipo pequeño.

Convención: cada hallazgo lleva su fuente; lo que no pude verificar está en "Gaps". Versiones de referencia: Kubernetes v1.37 es la última release documentada en kubernetes.io a fecha de hoy; `k8s.io/apimachinery`, `k8s.io/apiserver` y `k8s.io/client-go` van por v0.37.1 (publicado 23-sep-2026).

## 1. El patrón en sí: cabeceras, qué hay que eliminar, TLS/CA/SNI y cómo se ve en el audit log

### Takeaway
El patrón es estándar y está soportado de forma nativa por Kubernetes (cabeceras `Impersonate-User/Group/Uid/Extra-*` + verbo RBAC `impersonate`), y el audit log del apiserver registra al proxy en `user` y al desarrollador en `impersonatedUser`. Lo crítico en el proxy es (a) rechazar o eliminar `Authorization`, cualquier `Impersonate-*` y `X-Forwarded-For` que venga del cliente, y (b) que el kubeconfig apunte al proxy con la CA del proxy en `certificate-authority-data` (Pinniped publica esa CA en el status del `CredentialIssuer`).

### Cited Findings
- Cabeceras de impersonación: `Impersonate-User` (obligatoria y debe ir antes que el resto), `Impersonate-Group` (repetible), `Impersonate-Uid` (requiere Kubernetes v1.22+), `Impersonate-Extra-<fieldname>`; las claves de extra que no sean nombres válidos de cabecera HTTP deben ir percent-encoded; kubectl expone `--as`, `--as-group` y `--as-uid` — [Kubernetes: Authenticating, sección User impersonation](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- RBAC: el verbo `impersonate` se aplica a los recursos `users`, `groups`, `serviceaccounts`, `uids` y `userextras` (ejemplo de ClusterRole `impersonator` con `apiGroups: [""]`, esos recursos y `verbs: ["impersonate"]`); según el resumen de la página, al impersonar se añade automáticamente el grupo `system:authenticated` salvo que se especifiquen grupos explícitamente — [Kubernetes: Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- Audit log (`audit.k8s.io/v1` `Event`): campo `user` ("Authenticated user information", obligatorio) y campo `impersonatedUser` ("Impersonated user information", tipo `authentication/v1.UserInfo`); `sourceIPs` se rellena en este orden: IPs de `X-Forwarded-For`, luego `X-Real-Ip` si no está ya, luego la remote address; `userAgent` "is provided by the client, and must not be trusted"; niveles de policy `None`, `Metadata`, `Request`, `RequestResponse` — [Kubernetes: kube-apiserver Audit Configuration (v1)](https://kubernetes.io/docs/reference/config-api/apiserver-audit.v1/)
- Ejemplo real de cómo aparece en el audit log del cluster una petición impersonada por un proxy comercial: `"impersonatedUser": {"username": "alice_glick", "groups": ["system:authenticated"]}` — [StrongDM: Identity Alias for Kubernetes](https://docs.strongdm.com/admin/resources/clusters/kubernetes-identity-alias/)
- Pinniped (impersonator.go) rechaza la petición si todavía llega una cabecera `Authorization` al handler (mensaje: "aggregated API server logic did not delete authorization header"), rechaza cualquier cabecera cuyo nombre empiece por `Impersonate` (`ensureNoImpersonationHeaders`: "header already exists"), y borra `X-Forwarded-For` del cliente con el comentario "do not allow the client to cause log confusion by spoofing this header" — [vmware/pinniped internal/concierge/impersonator/impersonator.go](https://github.com/vmware/pinniped/blob/main/internal/concierge/impersonator/impersonator.go)
- Pinniped aplica la impersonación con `transport.ImpersonationConfig{UserName, Groups, Extra}` + `transport.NewImpersonatingRoundTripper`, y en "nested impersonation" (el usuario hace `kubectl --as` a través del proxy) guarda el usuario original en un extra `original-user-info.impersonation-proxy.concierge.pinniped.dev` (JSON) "to make sure that the Kubernetes audit log contains all three identities (original user, impersonated user and the impersonation proxy's service account)"; el código además declara que no puede impersonar UIDs ("unable to impersonate uid") y, cuando la identidad viene de un bearer token con UID (service accounts), reenvía el bearer token original sin cabeceras de impersonación — [impersonator.go](https://github.com/vmware/pinniped/blob/main/internal/concierge/impersonator/impersonator.go)
- Pinniped autentica a los clientes del impersonation proxy con certificados de cliente firmados por su propia CA (`impersonationProxySignerCA` unida a la CA de clientes del kube-apiserver mediante `dynamiccertificates.NewUnionCAContentProvider`) o con bearer tokens validados contra `TokenCredentialRequest` — [impersonator.go](https://github.com/vmware/pinniped/blob/main/internal/concierge/impersonator/impersonator.go)
- kube-oidc-proxy: "Since impersonation is utilized for forwarding, user-submitted impersonation headers are disabled to prevent bypass attempts"; añade `Impersonate-User`, `Impersonate-Group` e `Impersonate-Extra` a partir de la respuesta OIDC — [jetstack/kube-oidc-proxy README](https://github.com/jetstack/kube-oidc-proxy)
- Rancher: el authentication proxy "authenticates the caller and sets the proper Kubernetes impersonation headers before forwarding the call to Kubernetes masters"; en el cluster downstream crea por usuario el namespace `cattle-impersonation-system`, una service account `cattle-impersonation-<user ID>`, su token, un ClusterRole y un ClusterRoleBinding, de modo que "Each service account can only impersonate one user, preventing privilege escalation" — [Rancher: Communicating with Downstream User Clusters](https://ranchermanager.docs.rancher.com/reference-guides/rancher-manager-architecture/communicating-with-downstream-user-clusters)
- TLS del proxy en Pinniped: el diseño genera y persiste una CA propia ("Generate and persist a certificate authority for serving the impersonation proxy endpoint"), emite un serving cert para el `ExternalName` del Service `type: LoadBalancer` y rota la CA ("generate a CA and persist it in a Secret with some rotation period") — [Pinniped: API Design Proposal: Impersonation Proxy (HackMD)](https://hackmd.io/@pinniped/ryE5LfwlO)
- Desde Pinniped v0.25.0 el serving cert puede gestionarse externamente: `spec.impersonationProxy.tls.secretName` y `spec.impersonationProxy.tls.certificateAuthorityData` en el `CredentialIssuer`; la CA configurada se publica en `status.strategies[*].frontend.impersonationProxyInfo.certificateAuthorityData` para que los clientes generen el kubeconfig; el post usa cert-manager y un Contour `HTTPProxy` con `tcpproxy` y `virtualhost.tls.passthrough: true` para preservar el mTLS hasta el proxy — [Pinniped v0.25.0 release post](https://pinniped.dev/posts/v0-25-0-external-cert-mgmt-impersonation-proxy/)
- `externalEndpoint` "is the endpoint which the client should use to connect to the impersonation proxy. If left unset, the client will default to connecting based on the ClusterIP or LoadBalancer endpoint"; con `service.type: None` es obligatorio fijar `externalEndpoint` — [Pinniped generated API README](https://github.com/vmware/pinniped/blob/main/generated/latest/README.adoc)
- Teleport usa SNI y ALPN para enrutar en un único puerto: "All Teleport clients including SSH, web browser, kubectl, database and reverse tunnel clients establish a TLS tunnel to the proxy's web port and indicate the protocol they're requesting using SNI and ALPN TLS extensions" — [Teleport: TLS Routing](https://goteleport.com/docs/reference/architecture/tls-routing/)
- `boundary connect kube` "passes the specified host name through to the client for use in the TLS SNI value, if supported" — [Boundary: connect kube](https://developer.hashicorp.com/boundary/docs/commands/connect/kube)
- Alternativa al patrón para clusters self-managed: el "authenticating proxy" nativo (`--requestheader-username-headers`, `--requestheader-group-headers`, `--requestheader-extra-headers-prefix`, `--requestheader-client-ca-file`, `--requestheader-allowed-names`; cabeceras `X-Remote-User`, `X-Remote-Group`, `X-Remote-Extra-*`; requiere certificado de cliente del proxy) — [Kubernetes: Authenticating, sección Authenticating Proxy](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)

### Inferences
- Lista mínima de lo que el proxy debe eliminar/reescribir antes de reenviar: (1) `Authorization` del cliente (se sustituye por el token de la service account del proxy en ese cluster); (2) toda cabecera `Impersonate-*` entrante (o, si se quiere soportar `kubectl --as` "nested", hay que autorizarla contra RBAC en el proxy y reinyectarla de forma controlada, como hace Pinniped reutilizando el filtro de impersonación de `k8s.io/apiserver`); (3) `X-Forwarded-For`/`X-Real-Ip` del cliente, sustituidas por la IP real vista por el proxy, porque el apiserver copia XFF en `sourceIPs` sin comprobación de confianza; (4) hop-by-hop headers (`httputil.ReverseProxy` ya lo hace).
- Como el proxy termina TLS, el kubeconfig entregado al desarrollador debe llevar `server: https://<proxy>` y `certificate-authority-data` con la CA del proxy (o una CA pública si se usa cert-manager/ACME); la CA del apiserver real solo la necesita el proxy en su transporte upstream. Con varios clusters detrás de una sola IP, el SNI del ClientHello es lo que permite elegir certificado/ruta por hostname (modelo Teleport); con un path prefix se puede usar un único certificado.
- Diseños basados en mTLS con certificados de cliente (Pinniped) obligan a que cualquier LB/ingress delante haga TLS passthrough; si la app emite tokens en lugar de certificados, se puede terminar TLS en un LB/ingress normal.
- En el audit log del cluster el "quién" queda en `impersonatedUser` y el "a través de qué" en `user` (SA del proxy); si se quiere conservar más contexto (sesión, token id, IP original) hay dos vías: (a) meterlo en `Impersonate-Extra-*` (patrón `original-user-info` de Pinniped), o (b) correlacionar el log propio del proxy con el evento del apiserver.

### Gaps
- No pude confirmar en fuentes primarias si el impersonation proxy de Pinniped comparte puerto con su aggregated API server y distingue el tráfico por SNI (solo encontré referencias a SNI en el Supervisor y en el tema de ingress).
- No verifiqué el campo `tls-server-name` del kubeconfig (existe en client-go, pero no lo cité desde una fuente fetchada); es relevante si el proxy se expone por IP o si el hostname del kubeconfig difiere del SNI esperado.
- El texto exacto de kubernetes.io sobre la adición automática de `system:authenticated` al impersonar viene del resumen del fetch, no de una cita literal.

## 2. Cobertura de protocolo: SPDY vs WebSockets (KEP-4006), watch, logs -f, kubectl proxy, y `httputil.ReverseProxy`

### Takeaway
Desde Kubernetes 1.30/1.31 kubectl intenta WebSockets primero (exec/attach/cp con `v5.channel.k8s.io`, port-forward con `v2.portforward.k8s.io`) y cae a SPDY si falla; la GA está planificada para v1.38. Para el proxy es irrelevante cuál de los dos llegue: ambos son `Connection: Upgrade` sobre HTTP/1.1 y Go `httputil.ReverseProxy` los tuneliza de forma genérica vía `Hijacker`, siempre que el upstream se hable en HTTP/1.1 (el kube-apiserver no acepta upgrades sobre HTTP/2). `watch` y `logs -f` son respuestas chunked sin `Content-Length`, que `ReverseProxy` vuelca sin buffering. Los que rompen esto en la práctica son los LB/ingress intermedios (idle timeouts de 60 s, límites de body de 1 MB) y proxies que negocian HTTP/2 con el upstream.

### Cited Findings
- Motivación del KEP: "The SPDY streaming protocol has been deprecated since 2015, and by now many proxies, gateways, and load-balancers do not support SPDY" y la transición a WebSockets "is necessary to enable the aforementioned intermediaries" — [KEP-4006 README](https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/4006-transition-spdy-to-websockets/README.md)

- Feature gate `PortForwardWebsockets` (kube-apiserver): alpha, default `false`, 1.30; beta, default `true`, desde 1.31 (streaming WebSocket del subprotocolo port-forward para clientes que piden `v2.portforward.k8s.io`) — [kubernetes/website feature-gates/PortForwardWebsockets.md](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/PortForwardWebsockets.md)

### Inferences
- Un único camino genérico de `Upgrade` en el proxy cubre SPDY (`Upgrade: SPDY/3.1`) y WebSocket (`Upgrade: websocket`): `ReverseProxy` no inspecciona el tipo, solo exige HTTP/1.1 en ambos lados y `Hijacker` en el listener. Consecuencias prácticas: (1) el listener del proxy debe seguir ofreciendo `http/1.1` en ALPN (Go lo hace por defecto junto a `h2`); (2) el transporte upstream para peticiones con upgrade debe forzar HTTP/1.1 (patrón de Pinniped: dos RoundTrippers, elegido con `httpstream.IsUpgradeRequest`); (3) no meter middleware que envuelva el `ResponseWriter` sin reexportar `Hijacker` (es el fallo típico "non-Hijacker ResponseWriter").
- `kubectl cp` es `exec` + `tar`, así que hereda el mismo camino de upgrade; `kubectl logs -f` y `watch` no hacen upgrade: son GET con respuesta chunked sin `Content-Length`, y `ReverseProxy` los vuelca inmediatamente (ContentLength -1). Aun así conviene fijar `FlushInterval = -1` explícitamente por si un `ModifyResponse` o un `Content-Length` inesperado lo cambian.
- `kubectl proxy` es simplemente otro cliente client-go apuntando al kubeconfig; no necesita nada especial en el proxy de impersonación. Al contrario, `kubectl proxy` es la prueba de que client-go maneja base paths (`--append-server-path`).
- Timeouts a configurar en el proxy y en todo lo que haya delante: sin `WriteTimeout`/`ReadTimeout` globales en el `http.Server` para streams (o muy altos), idle timeouts de LB muy por encima de 60 s (un `exec` interactivo sin output o un `port-forward` inactivo se cortan con el default de 60 s de ALB/ingress-nginx; un `watch` del apiserver puede durar entre 1800 s y el doble), y sin límite de body de 1 MB (`kubectl apply` de manifests grandes y `kubectl cp` de subida lo exceden). Usar el keepalive TCP del `net.Dialer` y, si hay NLB/ALB en medio, alinear `idle_timeout`.
- Sobre `AuthorizePodWebsocketUpgradeCreatePermission` (beta desde 1.35): por su nombre, alinea la autorización de los upgrades WebSocket (que son GET) con el permiso `create` de `pods/exec` usado por SPDY (POST); no verifiqué la semántica exacta, pero implica que las reglas RBAC del desarrollador deben conceder `create` en `pods/exec`, `pods/attach`, `pods/portforward` independientemente del protocolo.

## 3. Cómo lo implementan las herramientas existentes

### Takeaway
Hay dos familias: (a) proxies de impersonación reales (Pinniped Concierge, kube-oidc-proxy —archivado—, Paralus, Teleport, Rancher, Pomerium, StrongDM Identity Alias, Tailscale operator en modo auth), que terminan TLS, validan identidad propia y reenvían con `Impersonate-*`; y (b) túneles L4 con credenciales brokeradas (Boundary, Cloudflare Tunnel) que no impersonan: el usuario actúa como la service account que recibe. De las open-source, Pinniped es la referencia de ingeniería más sólida (reutiliza el filter chain de `k8s.io/apiserver`), Teleport la más completa (session recording, reverse tunnels), Paralus la más parecida a "producto multi-cluster" pero con releases estancadas, y kube-oidc-proxy está archivado desde el 17-may-2024.

### Cited Findings
- Pinniped Concierge (impersonation proxy): "signs the short-lived client certificates using its own signing key" y "hosts an impersonation proxy that relays requests to the Kubernetes API server with the end user's identity and group memberships"; al recibir peticiones "Pinniped validates that the client's certificate was signed by its own key before submitting the API request to the Kubernetes API server on behalf of the user via impersonation as that user" — [Pinniped: Architecture](https://pinniped.dev/docs/background/architecture/)
- Por qué existe: la estrategia `TokenCredentialRequest` solo funciona en clusters "self-hosted" donde pueden correr pods en nodos con `kube-controller-manager` (la mayoría de managed no lo permiten), mientras que el impersonation proxy "Can be run on any Kubernetes cluster. Default configuration requires that a `LoadBalancer` service can be created" (o un ClusterIP/Service propio); clusters listados como soportados: TKG, kind, kubeadm, EKS, GKE, AKS; advertencia: no usar `--anonymous-auth=false` en clusters que no usen el impersonation proxy — [Pinniped: Supported cluster types](https://pinniped.dev/docs/reference/supported-clusters/)
- Pinniped: la propuesta de diseño contempla clusters gestionados (EKS, AKS, GKE) donde el control plane no es configurable, `Service type: LoadBalancer` automático, y publicar el endpoint y la CA en el status del recurso — [Pinniped design proposal (HackMD)](https://hackmd.io/@pinniped/ryE5LfwlO); petición de la comunidad para personalizar la CA del impersonation proxy y usarlo detrás de un ingress — [vmware/pinniped issue #1104](https://github.com/vmware/pinniped/issues/1104)
- Pinniped está construido sobre la librería `k8s.io/apiserver` (`recommendedOptions.SecureServing`, `Authentication.ClientCert.CAContentProvider`, audit context `ac.GetEventUser()`/`ac.GetEventImpersonatedUser()`, "wire up a fake audit backend at the metadata level so we can preserve the original user during nested impersonation") — [impersonator.go](https://github.com/vmware/pinniped/blob/main/internal/concierge/impersonator/impersonator.go)
- jetstack/kube-oidc-proxy: "This repository was archived by the owner on May 17, 2024. It is now read-only"; valida tokens OIDC, añade `Impersonate-User/Group/Extra`, deshabilita cabeceras de impersonación del usuario, documenta auditing, TLS de servicio y "token passthrough"; el README recomienda el fork mantenido por Tremolo Security — [jetstack/kube-oidc-proxy](https://github.com/jetstack/kube-oidc-proxy)
- Paralus: Apache-2.0, "CNCF Sandbox project", mantenido por Rafay; promete "Automatic logging of all user actions performed for audit and compliance purposes" y "Dynamic and immediate changing and revoking of permissions"; acceso vía GUI, CLI `pctl` o API — [paralus/paralus README](https://github.com/paralus/paralus)
- Paralus, componentes: el Relay Server "Acts as a KubeAPI proxy and enforces access policies at the edge", acepta conexiones en `*.user.domain-name` y `core-connector.domain-name` con "TLS termination with client certificate validation", "forwards only authenticated and authorized kubectl requests to the cluster" y mantiene canales gRPC con los relay agents; el Relay Agent en el cluster "establishes a gRPC channel with sentry service to register the cluster", reenvía las peticiones kubectl al kube-apiserver y crea service accounts just-in-time según la policy; Sentry "generates unique kubeconfig file for each user based on the policy definition" — [Paralus: Core Components](https://www.paralus.io/docs/architecture/core-components); repo del relay — [paralus/relay](https://github.com/paralus/relay)
- Paralus, mantenimiento: últimas releases v0.3.0 (16-ene-2025), v0.2.9 (23-may-2024), v0.2.8 (14-jun-2023), v0.2.7 (28-feb-2023), v0.2.6 (22-dic-2022) — [paralus/paralus releases](https://github.com/paralus/paralus/releases). A fecha de hoy (sep-2026) llevan ~20 meses sin release.
- Teleport, controles: "The Kubernetes Service uses impersonation headers to send requests to the API server with one Kubernetes user and zero or more Kubernetes groups"; su service account necesita un ClusterRole con `impersonate` sobre `users`, `groups`, `serviceaccounts`, más `get` en `pods` y `create` en `selfsubjectaccessreviews`; "If a user has exactly one value in `kubernetes_users`, the Teleport Kubernetes Service impersonates that user"; "If there are no values or a wildcard (`*`) in `kubernetes_users`, the Kubernetes Service uses the user's Teleport username"; `tsh kube login --as/--as-groups` para elegir manualmente; aviso: salvo que se impersonen grupos manualmente, "the Kubernetes Service will automatically impersonate any groups within `kubernetes_groups`" — [Teleport: Kubernetes Access Controls](https://goteleport.com/docs/enroll-resources/kubernetes-access/controls/)
- Teleport, conectividad y auth: "Teleport Agents dial the Teleport Proxy Service to establish a reverse tunnel. Client traffic flows via the Proxy Service to the agent, and the agent forwards traffic to resources" — [Teleport: Agent Architecture](https://goteleport.com/docs/reference/architecture/agents/); los clientes reciben "a client certificate, which automatically works for all resources protected by Teleport" y hay "recordings of interactive sessions established via SSH, RDP and `kubectl` commands" reproducibles — [Teleport: How it works, Kubernetes](https://goteleport.com/teleport/how-it-works/secure-kubernetes-access/)
- Teleport, session recording: "Windows, database, and Kubernetes sessions are always recorded at the host running the Teleport service for this session type, since there is no Teleport software running on the 'node'"; por eso los modos node/proxy se tratan igual (grabación asíncrona) y node-sync/proxy-sync igual (síncrona) — [Teleport: Session Recording](https://goteleport.com/docs/reference/architecture/session-recording/)
- Rancher: `cattle-cluster-agent` "Communicates between the cluster and Rancher server (through a tunnel to the cluster controller)"; el kubeconfig generado por defecto proxya a través del servidor Rancher; el Authorized Cluster Endpoint (ACE) "allows users to connect to the Kubernetes API server of a downstream cluster without having to route their requests through the Rancher authentication proxy" (RKE2/K3s), útil "when Rancher is down or reducing latency for geographically distant clusters", con el webhook `kube-api-auth` para autenticar — [Rancher: Communicating with Downstream User Clusters](https://ranchermanager.docs.rancher.com/reference-guides/rancher-manager-architecture/communicating-with-downstream-user-clusters); el kubeconfig descargado tiene varios contexts: "when you use `kubectl` with the first context, `my-cluster`, you will be authenticated through the Rancher server" y con el segundo "you would authenticate with the authorized cluster endpoint" — [Rancher: Access a Cluster with kubectl and kubeconfig](https://ranchermanager.docs.rancher.com/how-to-guides/new-user-guides/manage-clusters/access-clusters/use-kubectl-and-kubeconfig)
- Pomerium: dos métodos, "User Impersonation" (route con `to:` al apiserver, `tls_custom_ca` con la CA del apiserver, `kubernetes_service_account_token`; ClusterRole con `impersonate` en `users`/`groups`, opcionalmente `resourceNames`) y "Pomerium JWT" (Kubernetes 1.30+, `set_request_headers: Authorization: 'Bearer ${pomerium.jwt}'`); kubeconfig con `exec: command: pomerium-cli, args: [k8s, exec-credential, <route-url>]` — [Pomerium: Kubernetes kubectl Integration](https://www.pomerium.com/docs/capabilities/kubernetes-access); issue sobre poblar `Impersonate-Group` con claims de grupos — [pomerium/pomerium issue #2221](https://github.com/pomerium/pomerium/issues/2221)
- HashiCorp Boundary: "TCP targets provide a generic way to connect to any service Boundary has access to, including Kubernetes API servers"; "You can configure TCP targets with credential brokering, but not credential injection" — [Boundary: Create a Kubernetes TCP target](https://developer.hashicorp.com/boundary/docs/targets/create/tcp/kubernetes); `boundary connect kube` "authorizes a session against a target and invokes a Kubernetes client for the connection. The command fills in the local address and port" (`-style kubectl`) — [Boundary: connect kube](https://developer.hashicorp.com/boundary/docs/commands/connect/kube); el tutorial brokerea "a short-lived Kubernetes service account token" desde Vault y el usuario ejecuta `kubectl ... --server=$KUBE_API_URL --token=$BROKERED_KUBE_TOKEN` (en el tutorial incluso con `--insecure-skip-tls-verify`), es decir, actúa como la service account — [Boundary tutorial: Connect to Kubernetes](https://developer.hashicorp.com/boundary/tutorials/kubernetes-connect/kubernetes-getting-started-connect)
- StrongDM: el recurso Kubernetes se conecta vía "StrongDM gateways or relays", con credenciales `certificate-authority`, `client-certificate`, `client-key` (mTLS) e Identity Aliases opcionales; soporta exec, attach, cp y port-forward — [StrongDM: Kubernetes](https://docs.strongdm.com/admin/resources/clusters/kubernetes); Identity Alias: "The initial connection is made to the Kubernetes endpoint using the leased identity" y "The request also includes headers containing the individual user's Identity Alias username and role(s)"; ClusterRole con `impersonate` en `users`; el alias se configura en el perfil del usuario (p. ej. `alice_glick`) y aparece en `impersonatedUser` del audit log — [StrongDM: Identity Alias for Kubernetes](https://docs.strongdm.com/admin/resources/clusters/kubernetes-identity-alias/)
- Tailscale Kubernetes operator API server proxy: en modo auth (default) "The request is impersonated as the Tailscale user (for example, `alice@example.com`)"; para nodos con tags "The request is impersonated as a user with the node's FQDN, with the node's tags as Kubernetes groups"; modo noauth "forwards requests to the API server without adding authentication information"; kubeconfig con `tailscale configure kubeconfig <proxy-hostname>`; despliegue in-process (comparte ciclo de vida del operator, latencia inicial por provisión de certificados) o `ProxyGroup` dedicado ("provisioning certificates before becoming ready", para HA); limitación: "The proxy runs inside the cluster. If the cluster cannot schedule pods, you may lose access to the API" — [Tailscale KB 1437](https://tailscale.com/kb/1437/kubernetes-operator-api-server-proxy)
- Tailscale, grants: `"tailscale.com/cap/kubernetes": [{"impersonate": {"groups": ["system:masters"]}}]`; "Impersonate-User is set to the Tailscale user's login name"; para tagged devices "Impersonate-User is set to the node's FQDN" y los tags van como grupos si no hay grants; ejemplos `kubectl create clusterrolebinding ... --group="tag:k8s-readers"` — [Tailscale: Configure Kubernetes RBAC for the API server proxy](https://tailscale.com/docs/kubernetes-operator/api-server-access/auth-and-rbac)
- Tailscale, grabación: graba `kubectl exec`, `debug`, `attach` y `run` ("the command sent, `stdout` and `stderr` output, pod and container context, and the Tailscale identity"; "`stdin` is not recorded"); opcionalmente "all Kubernetes API requests passing through the proxy are recorded" (verbo, recurso, HTTP, user agent, identidad); el proxy "streams session data to a `tsrecorder` instance over your tailnet, end-to-end encrypted using WireGuard"; políticas "Fail open (default)" y "Fail closed" — [Tailscale: kubectl session and API request recording](https://tailscale.com/docs/features/kubernetes-operator/how-to/session-recording)
- Envoy ext_authz: el filtro sobrescribía cabeceras repetidas, bloqueando la integración con el authenticating proxy de Kubernetes, que necesita p. ej. `X-Remote-Group: dogs` y `X-Remote-Group: dachshunds` como cabeceras separadas; abierto 12-may-2020, cerrado con PR #11158 — [envoyproxy/envoy issue #11156](https://github.com/envoyproxy/envoy/issues/11156); un artículo de 2023-24 describe un proxy Envoy con ext_authz que inyecta `Impersonate-*` y afirma que el ext_authz gRPC solo pasa un `Impersonate-Group` mientras que el HTTP permite varios (fuente secundaria, sin verificar) — [Medium: Streamlining Multi-Cloud Kubernetes Access Using OIDC](https://medium.com/@mnkg561/streamlining-multi-cloud-kubernetes-access-using-oidc-a1380dd1a6af)
- vCluster Platform (antes Loft): "By default, all Kubernetes contexts created through vCluster Platform route Kubernetes traffic (such as kubectl get pods) through the central vCluster Platform instance"; los "Regional Cluster Endpoints" evitan ese salto y "handle authentication, authorization, and other functions directly within the connected cluster through the installed vCluster Platform agent", exponiendo el agent por Ingress o LoadBalancer/NodePort con HTTPS y la anotación `loft.sh/direct-cluster-endpoint` — [vCluster: Regional Cluster Endpoints](https://www.vcluster.com/docs/platform/administer/clusters/advanced/regional-cluster-endpoints); el agent "utilizes a pre-shared key to reach the control plane, authenticate itself, and establish a secure WireGuard-based, user-space tunnel" con fallback a relay DERP a través del control plane — [vCluster: Platform communication and connectivity](https://www.vcluster.com/docs/platform/understand/platform_communication); repo histórico — [loft-sh/loft](https://github.com/loft-sh/loft)

### Inferences
- Patrón común a todas las implementaciones "reales": una credencial privilegiada por cluster (SA con `impersonate`), validación de identidad propia en el borde, y reenvío con `Impersonate-*`. Rancher y Paralus refinan el privilegio (SA por usuario / JIT) para limitar el blast radius de la credencial del proxy; Teleport y Tailscale lo mantienen en una SA única pero con mapeo de roles/grants.
- Para un equipo pequeño, la lección de Pinniped es que construir sobre `k8s.io/apiserver` (filtros de authn, impersonation, audit) evita reimplementar el stripping de cabeceras y el nested impersonation; la de Pomerium/tuist/StrongDM es que el manejo de upgrades y HTTP/2 es donde fallan hasta los productos maduros.
- Boundary y Cloudflare Tunnel no resuelven "identidad por desarrollador en el audit log del cluster": el cluster ve la SA brokerada. Son opciones de conectividad, no de impersonación.

### Gaps
- No obtuve la versión actual de Pinniped ni de Teleport/Tailscale operator (no consulté sus páginas de releases); Pinniped y Tailscale muestran actividad reciente (posts/docs), pero no lo cuantifiqué.
- No verifiqué el estado del fork TremoloSecurity/kube-oidc-proxy.
- StrongDM: un snippet de búsqueda indicaba que los tipos legacy "User Impersonation" están deprecados con fin de vida el 31-ene-2027 (presumiblemente en [su changelog](https://docs.strongdm.com/changelog/monthly-recap)), pero la página específica devolvió 404 y no pude confirmarlo.

## 4. Llegar a clusters privados desde un proxy central: túneles inversos vs reachability directa

### Takeaway
Todas las plataformas multi-cluster (Teleport, Paralus, Rancher, vCluster Platform) resuelven los clusters privados con un agent dentro del cluster que abre una conexión saliente persistente (reverse tunnel gRPC/WebSocket/WireGuard) hacia el proxy central; Cloudflare Tunnel y Tailscale hacen lo mismo a nivel de red sin impersonación propia. Konnectivity (apiserver-network-proxy) no sirve para esto: está pensado para el tráfico de salida del apiserver hacia los nodos. La alternativa "el proxy alcanza directamente cada API server" es más simple pero exige endpoints públicos o peering/VPN por cluster.

### Cited Findings
- Teleport: "Multiple Kubernetes clusters connect to it over reverse tunnels"; "Teleport Agents dial the Teleport Proxy Service to establish a reverse tunnel. Client traffic flows via the Proxy Service to the agent, and the agent forwards traffic to resources in your infrastructure" — [Teleport: Agent Architecture](https://goteleport.com/docs/reference/architecture/agents/); "A Teleport Agent runs in the same network as a target resource and speaks its native protocol" — [Teleport: How it works](https://goteleport.com/teleport/how-it-works/secure-kubernetes-access/)
- Paralus: el Relay Agent en el cluster "establishes a gRPC channel with sentry service to register the cluster" y el Relay Server mantiene "a long lasting channel between agents deployed in cluster using gRPC" — [Paralus: Core Components](https://www.paralus.io/docs/architecture/core-components)
- Rancher: "Each downstream cluster has a cluster agent opening a tunnel to its corresponding cluster controller in the Rancher server"; si el agent no está disponible, `rancher-system-agent` (RKE2/K3s) "creates a tunnel to the cluster controller to communicate with Rancher" — [Rancher: Communicating with Downstream User Clusters](https://ranchermanager.docs.rancher.com/reference-guides/rancher-manager-architecture/communicating-with-downstream-user-clusters)
- vCluster Platform: túnel WireGuard user-space iniciado por el agent con pre-shared key, con fallback a "Designated Encrypted Relay for Packets" (DERP) vía el control plane — [vCluster: Platform communication](https://www.vcluster.com/docs/platform/understand/platform_communication)
- Cloudflare Tunnel para kubectl: `cloudflared` en el cluster con un ingress rule `service: tcp://kubernetes.docker.internal:6443` y `originRequest: proxyType: socks`; "a secure, outbound-only connection between this machine and Cloudflare's network" sin puertos abiertos; en el cliente `cloudflared access tcp --hostname azure.widgetcorp.tech --url 127.0.0.1:1234` crea un SOCKS local tras autenticarse con el SSO; como "kubeconfig does not support proxy command configurations at this time" se usa `alias kubeone="env HTTPS_PROXY=socks5://127.0.0.1:1234 kubectl"`; al ser un túnel TCP crudo, el TLS y la autenticación del API server se preservan extremo a extremo — [Cloudflare: Connect through Cloudflare Access using kubectl](https://developers.cloudflare.com/cloudflare-one/tutorials/kubectl/); variante con credential plugin de client-go — [Cloudflare: Use Cloudflare Tunnels with Kubernetes client-go credential plugins](https://developers.cloudflare.com/cloudflare-one/tutorials/tunnel-kubectl/)
- Tailscale: el proxy corre dentro del cluster y se alcanza por su nombre MagicDNS en la tailnet (sin LB entrante) — [Tailscale KB 1437](https://tailscale.com/kb/1437/kubernetes-operator-api-server-proxy)
- Konnectivity: proxy server junto al apiserver y agents en la red de nodos que "establish a reverse tunnel over gRPC" ("Frontend client =HTTP over GRPC=> (:8090) proxy (:8091) <=GRPC= agent =HTTP=> http-test-server"); diseñado para el tráfico saliente del apiserver (exec, logs, webhooks, aggregated APIs), no para clientes externos; modos gRPC y `--mode=http-connect`; versionado alineado con el minor de Kubernetes desde 0.28.0 — [kubernetes-sigs/apiserver-network-proxy](https://github.com/kubernetes-sigs/apiserver-network-proxy)
- Pinniped asume reachability directa: el impersonation proxy se expone con un Service `LoadBalancer` (o ClusterIP/ingress propio) al que el cliente llega — [Pinniped: Supported cluster types](https://pinniped.dev/docs/reference/supported-clusters/)

### Inferences
- Trade-offs. Reachability directa (proxy → apiserver): sin componente en el cluster, sin túnel que mantener, pero requiere que cada API server sea alcanzable desde el proxy (endpoint público con allowlist de IPs del proxy en EKS/GKE/AKS, o VPC peering/VPN para private endpoints), y el proxy debe guardar CA + token por cluster. Reverse tunnel (agent → proxy): funciona con clusters totalmente privados y detrás de NAT, no exige abrir nada entrante, y permite que el agent sea quien tenga la SA privilegiada (mejor blast radius); a cambio hay que operar un agent por cluster, un multiplexor de streams en el proxy (gRPC/yamux/WebSocket) y toda la lógica de reconexión, y el path de exec/port-forward se vuelve túnel-dentro-de-túnel.
- Para el entorno del equipo (managed + self-managed, equipo pequeño): empezar con reachability directa es lo "esencial"; el reverse tunnel es "opcional" y solo se justifica si hay clusters sin endpoint alcanzable. Si se necesita, reutilizar un túnel L4 existente (Tailscale/Cloudflare) entre el proxy y el apiserver es más barato que escribir un relay propio al estilo Paralus.
- Konnectivity y el propio mecanismo de exec del apiserver muestran que un stream kubectl ya atraviesa al menos dos saltos (apiserver → kubelet); cada túnel adicional añade latencia y otro punto de idle timeout.

### Gaps
- No consulté documentación de inlets ni de chisel; no puedo citar su estado de mantenimiento ni sus características.
- No encontré cifras de latencia añadida por los reverse tunnels de ninguna de las plataformas.

## 5. Rendimiento, HA, TLS/certificados y direccionamiento (SNI/subdominio vs path prefix)

### Takeaway
Ninguna fuente publica benchmarks de latencia del proxy; el coste real es operativo: el proxy pasa a estar en el camino crítico de todo acceso (Tailscale lo advierte, Rancher y vCluster añaden "bypass endpoints" precisamente por disponibilidad y latencia). Para HA basta un Deployment con ≥2 réplicas sin estado detrás de un LB L4 con idle timeouts altos; el TLS lo puede emitir cert-manager (Pinniped lo soporta desde v0.25.0). Para el direccionamiento, kubectl/client-go soportan oficialmente un path prefix en `server` (Rancher lo usa: `https://rancher/k8s/clusters/<id>`), lo que permite un único hostname y certificado; un hostname por cluster con SNI (Teleport) es la alternativa cuando se quiere separar certificados o rutas por TLS.

### Cited Findings
- client-go `rest.Config.Host`: "Host must be a host string, a host:port pair, or a URL to the base of the apiserver. If a URL is given then the (optional) Path of that URL represents a prefix that must be appended to all request URIs used" (v0.37.1) — [pkg.go.dev k8s.io/client-go/rest](https://pkg.go.dev/k8s.io/client-go/rest#ImpersonationConfig)
- `kubectl proxy --append-server-path`: "If true, enables automatic path appending of the kube context server path to each request" — [kubectl proxy reference](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_proxy/)
- Ejemplo de kubeconfig de Rancher con path prefix: `server: https://rancher.example.com/k8s/clusters/c-m-abc12345` y `token: token-xxxxx:yyyyyyyy` (fuente secundaria) — [OneUptime: How to Download kubeconfig from Rancher](https://oneuptime.com/blog/post/2026-03-19-rancher-download-kubeconfig/view); el kubeconfig de Rancher enruta por defecto a través del servidor Rancher — [Rancher: Access a Cluster with kubectl and kubeconfig](https://ranchermanager.docs.rancher.com/how-to-guides/new-user-guides/manage-clusters/access-clusters/use-kubectl-and-kubeconfig)
- Teleport: un solo puerto (`web_listen_addr`) para todos los clientes, enrutado por SNI/ALPN — [Teleport: TLS Routing](https://goteleport.com/docs/reference/architecture/tls-routing/)
- Tailscale: "In-Process" (comparte ciclo de vida del operator) vs `ProxyGroup` dedicado para HA; "In-cluster dependency: The proxy runs inside the cluster. If the cluster cannot schedule pods, you may lose access to the API"; latencia en la primera petición por provisión de certificados en modo in-process — [Tailscale KB 1437](https://tailscale.com/kb/1437/kubernetes-operator-api-server-proxy)
- Rancher justifica el Authorized Cluster Endpoint para acceder "when Rancher is down or reducing latency for geographically distant clusters" — [Rancher: Communicating with Downstream User Clusters](https://ranchermanager.docs.rancher.com/reference-guides/rancher-manager-architecture/communicating-with-downstream-user-clusters); vCluster Platform ofrece Regional Cluster Endpoints para no "rerouting traffic to the central vCluster Platform instance" — [vCluster: Regional Cluster Endpoints](https://www.vcluster.com/docs/platform/administer/clusters/advanced/regional-cluster-endpoints)
- Pinniped: certificado del impersonation proxy emitido por cert-manager (`ClusterIssuer` + `Certificate` → Secret referenciado en `spec.impersonationProxy.tls.secretName`) y CA publicada en el status para los kubeconfigs — [Pinniped v0.25.0 post](https://pinniped.dev/posts/v0-25-0-external-cert-mgmt-impersonation-proxy/)
- Límites del apiserver que el proxy hereda: `--request-timeout` 60 s y watches de al menos `--min-request-timeout` 1800 s — [kubernetes-client/python: watch timeout settings](https://github.com/kubernetes-client/python/blob/master/examples/watch/timeout-settings.md); el apiserver cachea respuestas del webhook de tokens `--authentication-token-webhook-cache-ttl` por defecto `2m0s` — [Kubernetes: kube-apiserver reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/)
- LB delante del proxy: ALB idle timeout 60 s por defecto — [AWS: Application Load Balancers](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html); ingress-nginx `proxy-read-timeout`/`proxy-send-timeout` 60 s y `proxy-body-size` 1m — [ingress-nginx ConfigMap](https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/configmap/)
- `UpgradeAwareHandler` incluye `MaxBytesPerSec` (rate limiting de upgrades) y `FlushInterval` — [pkg.go.dev k8s.io/apimachinery/pkg/util/proxy](https://pkg.go.dev/k8s.io/apimachinery/pkg/util/proxy)

### Inferences
- Latencia: el sobrecoste por petición es un handshake TLS extra (amortizado con keep-alive/HTTP/2 hacia el upstream), la validación del token (microsegundos con JWT o caché; un round-trip a DB si es opaco sin caché) y una copia de bytes. Para exec/port-forward el proxy solo copia bytes entre dos sockets, así que el impacto es de RTT geográfico, no de CPU. Sin benchmarks publicados, lo razonable es medir p50/p99 de `kubectl get` con y sin proxy en el mismo cluster.
- Límites de conexión: cada `watch`, `exec`, `port-forward` y `logs -f` es una conexión HTTP/1.1 upstream de larga duración; con HTTP/2 upstream para peticiones normales se multiplexa, pero los upgrades no. Dimensionar `MaxIdleConnsPerHost`, file descriptors y el número de réplicas en función de usuarios concurrentes × streams abiertos, no de RPS.
- Dónde correr el proxy: (a) Deployment en uno de los clusters (o en un cluster "management" dedicado) es lo más simple, pero crea la dependencia circular que Tailscale advierte (si ese cluster cae, se pierde el acceso a todos, incluido a él mismo); mitigación: un kubeconfig "break-glass" nativo por cluster guardado en un vault. (b) Externo (VM/contenedor fuera de Kubernetes) evita la dependencia a costa de otra pieza de infraestructura. Para un equipo pequeño: Deployment con 2-3 réplicas stateless en el cluster de management + break-glass.
- Direccionamiento: el path prefix (`https://k8s.example.com/clusters/<id>`) es el "esencial" para un equipo pequeño: un hostname, un certificado (cert-manager/ACME), un LB; el proxy extrae `<id>` y lo elimina antes de reenviar. Un hostname por cluster (`<id>.k8s.example.com`) requiere wildcard cert o SNI dinámico, pero es más robusto frente a herramientas que ignoren el path y permite enrutar en L4 sin terminar TLS (útil si se quiere passthrough mTLS al estilo Pinniped). Ambos son compatibles con kubectl.
- TLS del proxy con cert-manager es "esencial" si el proxy expone un hostname público; la CA propia estilo Pinniped es "opcional" y solo tiene sentido si se quiere mTLS con certificados de cliente de corta vida.

### Gaps
- No encontré benchmarks de latencia o throughput de ningún proxy de impersonación (Pinniped, Teleport, Paralus, Tailscale) ni del propio `httputil.ReverseProxy` en este escenario.
- No verifiqué si todas las herramientas del ecosistema (Helm, Lens, k9s, ArgoCD, Terraform providers) respetan el path prefix del `server`; client-go lo hace por diseño, pero clientes no basados en client-go podrían no hacerlo.
- No verifiqué límites de conexiones concurrentes ni de tamaño de cabeceras/body de ALB o GCLB para este uso.

## 6. Validación de tokens en el proxy: opaco vs JWT, caché, rate limiting, latencia de revocación

### Takeaway
Las fuentes primarias no comparan formatos de token para este caso, pero sí muestran los patrones en uso: Pinniped y Teleport usan certificados de cliente de corta vida firmados por su propia CA; Pomerium y Boundary entregan tokens de corta vida vía credential plugin / Vault; Paralus promete revocación inmediata gracias a que cada petición pasa por su relay. El propio kube-apiserver fija el precedente de caché de validación de tokens: 2 minutos por defecto para el webhook de tokens.

### Cited Findings
- kube-apiserver cachea las respuestas del webhook token authenticator: `--authentication-token-webhook-cache-ttl` "The duration to cache responses from the webhook token authenticator", default `2m0s` — [Kubernetes: kube-apiserver reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/); el mecanismo TokenReview y su caché se describen en "Webhook Token Authentication" — [Kubernetes: Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- Pinniped emite "short-lived client certificates" firmados con su propia clave y valida esa firma en cada petición al impersonation proxy — [Pinniped: Architecture](https://pinniped.dev/docs/background/architecture/)
- Teleport entrega al cliente un certificado que "automatically works for all resources protected by Teleport" — [Teleport: How it works](https://goteleport.com/teleport/how-it-works/secure-kubernetes-access/)
- Paralus: "Dynamic and immediate changing and revoking of permissions" y kubeconfig único por usuario generado por Sentry según la policy — [paralus/paralus README](https://github.com/paralus/paralus); [Paralus: Core Components](https://www.paralus.io/docs/architecture/core-components)
- Pomerium: `pomerium-cli k8s exec-credential` como credential plugin del kubeconfig (autenticación por navegador) y, alternativamente, "Pomerium JWT" inyectado como `Authorization: Bearer ${pomerium.jwt}` para Kubernetes 1.30+ — [Pomerium: Kubernetes](https://www.pomerium.com/docs/capabilities/kubernetes-access)
- Boundary: "returns a short-lived Kubernetes service account token so you can run `kubectl` without storing permanent cluster credentials" — [Boundary tutorial](https://developer.hashicorp.com/boundary/tutorials/kubernetes-connect/kubernetes-getting-started-connect)
- Tailscale: la identidad viene de la conexión de la tailnet (no hay token de app); los grants cambian la autorización sin reemitir credenciales — [Tailscale KB 1437](https://tailscale.com/kb/1437/kubernetes-operator-api-server-proxy)

### Inferences
- Token opaco + lookup en DB: revocación inmediata y auditoría de uso trivial, a cambio de un round-trip por petición; con una caché en memoria de N segundos (el apiserver usa 2 min como default sensato) la latencia de revocación pasa a ser N segundos, que suele ser aceptable. JWT firmado con expiración corta (5-15 min) + refresh vía credential plugin (`exec` en el kubeconfig, como pomerium-cli o `kubectl` plugins de cloud): validación local sin DB y sin estado, pero la revocación solo es efectiva al expirar salvo que se añada una denylist consultada en caché, lo que devuelve al primer modelo. Híbrido razonable para un equipo pequeño: JWT corto para la autenticación por petición + comprobación cacheada del estado del usuario/sesión (revocado, permisos cambiados) cada 30-120 s.
- Caché por token en el proxy: clave = hash del token, valor = identidad resuelta (user, groups, uid, extra) + expiración; nunca cachear más allá del `exp` del token. Para clusters con muchos `watch`, la validación solo ocurre al abrir la conexión, así que la revocación no corta streams ya abiertos: si se quiere, hay que llevar un registro de conexiones activas por usuario y cerrarlas al revocar (Teleport y Tailscale pueden hacerlo porque controlan la sesión; en un proxy propio hay que implementarlo).
- Rate limiting: el apiserver ya tiene su propio API Priority and Fairness, pero todas las peticiones llegarán con el mismo `user` (la SA del proxy), así que APF las tratará como un único cliente; conviene limitar por usuario en el proxy (token bucket por identidad) para que un `kubectl get -w` descontrolado no afecte a los demás, y limitar el número de upgrades concurrentes por usuario (`MaxBytesPerSec` del `UpgradeAwareHandler` solo limita ancho de banda).
- `kubectl --as` a través del proxy solo debe permitirse si el proxy autoriza la impersonación anidada (Pinniped/Teleport lo hacen); lo simple y seguro es rechazar `Impersonate-*` entrantes.

### Gaps
- No encontré una fuente que cuantifique la latencia de revocación o la política de caché de Teleport, Paralus o Tailscale para tokens/sesiones ya emitidos.
- No verifiqué si API Priority and Fairness distingue por `impersonatedUser` (asumo que usa el `user` autenticado, es decir, la SA del proxy).

## 7. Building blocks en Go (y equivalentes en TypeScript/Python)

### Takeaway
En Go existe todo lo necesario y está mantenido al ritmo de Kubernetes (v0.37.1): `httputil.ReverseProxy` para peticiones normales y upgrades, `k8s.io/apimachinery/pkg/util/proxy.UpgradeAwareHandler` (lo que usan kube-apiserver y `kubectl proxy`) como alternativa consciente de upgrades, `k8s.io/client-go/transport.NewImpersonatingRoundTripper` para las cabeceras, y `k8s.io/apiserver/pkg/audit` para contexto y eventos de auditoría (Pinniped demuestra que es viable construir el proxy entero sobre `k8s.io/apiserver`). En TypeScript el único bloque comparable es `http-proxy` (soporta `ws: true`), sin equivalente a `UpgradeAwareHandler` ni a `client-go/transport`; en Python no encontré bloques equivalentes maduros.

### Cited Findings
- `rest.Config.Impersonate` ("Impersonate is the configuration that RESTClient will use for impersonation") y `rest.ImpersonationConfig{UserName, UID, Groups, Extra map[string][]string}` (v0.37.1) — [pkg.go.dev k8s.io/client-go/rest](https://pkg.go.dev/k8s.io/client-go/rest#ImpersonationConfig)
- Uso real de `transport.ImpersonationConfig` + `transport.NewImpersonatingRoundTripper(impersonateConfig, delegate)` y `transport.NewBearerAuthRoundTripper(token, delegate)` como RoundTrippers upstream en un proxy de impersonación — [impersonator.go](https://github.com/vmware/pinniped/blob/main/internal/concierge/impersonator/impersonator.go)
- `k8s.io/apimachinery/pkg/util/proxy` (v0.37.1, publicado 23-sep-2026): `UpgradeAwareHandler` con `Transport`/`UpgradeTransport` separados, `WrapTransport` ("Applies default proxy behavior (URL rewriting, forwarded headers)"), `UseRequestLocation`, `UseLocationHost`, `FlushInterval`, `MaxBytesPerSec`, `Responder`, `RejectForwardingRedirects`, `UpgradeRequired`; además `Transport` (reescribe URLs en HTML), `UpgradeRequestRoundTripper`, `ErrorResponder`/`SimpleErrorResponder` — [pkg.go.dev k8s.io/apimachinery/pkg/util/proxy](https://pkg.go.dev/k8s.io/apimachinery/pkg/util/proxy)
- `k8s.io/apiserver/pkg/audit` (v0.37.1): `WithAuditContext()`, `AuditContextFrom()`, `WithAuditID()`, `AddAuditAnnotation(s)()`, `LogRequestObject()`, `LogResponseObject()`, `LogRequestPatch()`, `LogRequestMetadata()`, `LogImpersonatedUser()`, tipos `AuditContext`, `Sink`, `Backend` (con `Run`/`Shutdown`), `RequestAuditConfig`, `PolicyRuleEvaluator`, `EventString()`, `ObserveEvent()`, `Union()`; subpaquete `policy` — [pkg.go.dev k8s.io/apiserver/pkg/audit](https://pkg.go.dev/k8s.io/apiserver/pkg/audit)
- Detección de upgrades con `httpstream.IsUpgradeRequest(r)` y elección de transporte HTTP/1.1 vs HTTP/2 según el resultado; uso de `utilnet.CloneRequest` antes de modificar cabeceras — [impersonator.go](https://github.com/vmware/pinniped/blob/main/internal/concierge/impersonator/impersonator.go)
- `httputil.ReverseProxy` exige `http.Hijacker` en el `ResponseWriter` y HTTP/1.1 en la conexión entrante para upgrades; `Rewrite` (recomendado sobre `Director`) elimina hop-by-hop headers antes de llamar al hook y por defecto no preserva `X-Forwarded-*` entrantes, mientras que con `Director` sí se preservan (riesgo de spoofing) — [pkg.go.dev ReverseProxy](https://pkg.go.dev/net/http/httputil#ReverseProxy); [reverseproxy.go](https://github.com/golang/go/blob/master/src/net/http/httputil/reverseproxy.go)
- TypeScript/Node: `http-proxy` "supports websockets" y "You can activate the websocket support for the proxy using `ws:true` in the options"; el repo muestra 1.212 commits; la versión `dist-tags.latest` en npm es 1.18.1 — [http-party/node-http-proxy](https://github.com/http-party/node-http-proxy); [registry.npmjs.org/http-proxy](https://registry.npmjs.org/http-proxy)

### Inferences
- Esqueleto mínimo en Go para un equipo pequeño: `http.Server` con TLS (cert-manager), middleware de autenticación propio que resuelve el token a `user.Info`, y por ruta `/clusters/{id}/...` un `httputil.ReverseProxy` con `Rewrite` que (1) recorta el prefix, (2) borra `Authorization`, `Impersonate-*`, `X-Forwarded-*`, (3) pone `X-Forwarded-For` real, y cuyo `Transport` es `transport.NewImpersonatingRoundTripper(cfg, transport.NewBearerAuthRoundTripper(saToken, tlsTransport))`; para upgrades, un segundo transporte HTTP/1.1 (o `UpgradeAwareHandler` con `UpgradeTransport`). `FlushInterval = -1`. Esto cubre get/list/watch/logs/exec/attach/port-forward/cp/proxy sin código específico de protocolo.
- `k8s.io/apiserver/pkg/audit` es utilizable fuera de kube-apiserver (Pinniped lo hace y `k8s.io/apiserver` es una librería pública para aggregated API servers), pero arrastra el modelo de policy/backends del apiserver; para un proxy propio suele bastar con emitir eventos `audit.k8s.io/v1 Event` propios (tipos de `k8s.io/apiserver/pkg/apis/audit/v1`) rellenando `user`, `impersonatedUser`, `verb`, `requestURI`, `sourceIPs`, `responseStatus` y `auditID`, y enviarlos a un sink (fichero/webhook). Ventaja: mismo esquema que el audit log del cluster, lo que facilita correlar.
- TypeScript: `http-proxy` tuneliza el `upgrade` de Node (`server.on('upgrade', ...)`) y por tanto puede pasar SPDY igual que WebSocket (Node entrega cualquier `Upgrade` al evento), pero no hay equivalentes a `ImpersonatingRoundTripper` (hay que fijar las cabeceras a mano) ni a la caja de herramientas de audit; la madurez del ecosistema es claramente inferior. Python: no encontré ninguna librería de reverse proxy con soporte de `Upgrade` genérico pensada para este uso; un proxy en Python obligaría a trabajar a nivel de sockets/ASGI y no lo recomendaría para exec/port-forward.

### Gaps
- No pude confirmar la fecha de la última publicación de `http-proxy` 1.18.1 (npm devolvió 403 y el JSON del registry llegó truncado); tampoco su estado de mantenimiento más allá del contador de commits.
- No investigué `http-proxy-middleware` ni `@kubernetes/client-node` (soporte de exec por WebSocket) ni el cliente Python (`kubernetes.stream`), que serían los bloques del lado cliente, no del proxy.
- No verifiqué en fuentes primarias que Node entregue upgrades no-WebSocket (SPDY) al evento `upgrade` de `http.Server`; es una inferencia del funcionamiento general de Node.
