# Mecanismos nativos de Kubernetes para emitir, acotar, caducar y revocar credenciales (estado a septiembre de 2026)

Nota de método: las fuentes primarias son la documentación oficial de kubernetes.io (rama `main` del repo `kubernetes/website`, que documenta v1.37), los ficheros de feature gates del mismo repo, el código fuente de `kubernetes/kubernetes` en `master`, los CHANGELOG oficiales, los KEP y la documentación oficial de AWS/Google/Microsoft. Las versiones se citan como "alpha/beta/GA en vX.Y" según los ficheros de feature gates. Cuando una afirmación viene de un blog de terceros o de un issue de GitHub se indica explícitamente.

## 1. Tokens de ServiceAccount vía TokenRequest API (bound tokens)

### Takeaway
La TokenRequest API emite JWT firmados por el apiserver con caducidad configurable (mínimo 600 s, por defecto 1 h, techo por `--service-account-max-token-expiration` que *recorta* en vez de rechazar), vinculables a un Pod, Secret o Node cuya eliminación invalida el token (con hasta ~10 s de latencia por la caché de autenticación). Desde v1.32 (GA) cada token lleva `jti` y cada petición autenticada con él aparece en el audit log con `user.extra["authentication.kubernetes.io/credential-id"] = ["JTI=<uuid>"]`, lo que permite atribuir peticiones a una credencial emitida concreta; es el único mecanismo nativo que combina revocación real y atribución por credencial y funciona sin tocar flags del apiserver.

### Cited Findings
- Caducidad por defecto 1 h; configurable con `expirationSeconds`; el techo lo fija `--service-account-max-token-expiration` — [Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/)
- Validación de la API: `expirationSeconds` < 10 min → error "may not specify a duration less than 10 minutes"; > 2^32 s → "may not specify a duration larger than 2^32 seconds" — [validation.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/apis/authentication/validation/validation.go)
- Si se pide más que el máximo, el apiserver NO rechaza: emite un warning `requested expiration of %d seconds shortened to %d seconds` y recorta la duración (`if r.maxExpirationSeconds > 0 && req.Spec.ExpirationSeconds > r.maxExpirationSeconds`) — [token.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/registry/core/serviceaccount/storage/token.go); descripción del flag: "If an otherwise valid TokenRequest with a validity duration larger than this value is requested, a token will be issued with a validity duration of this value" — [kube-apiserver reference (v1.37)](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/). Un blog de terceros afirma que el apiserver "rechaza con un error de validación" — contradicho por el código fuente anterior; [oneuptime blog](https://oneuptime.com/blog/post/2026-02-09-serviceaccount-time-bound-tokens/view) es incorrecto en ese punto.
- El flag `--service-account-max-token-expiration` no muestra valor por defecto en la referencia (solo "duration"), y el código sólo aplica el recorte cuando `maxExpirationSeconds > 0` — [kube-apiserver reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/); [token.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/registry/core/serviceaccount/storage/token.go)
- `--service-account-extend-token-expiration` (Default: true): "admission injected tokens would be extended up to 1 year to prevent unexpected failure during transition, ignoring value of service-account-max-token-expiration" — [kube-apiserver reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/). En el código la extensión sólo se aplica si `r.extendExpiration && pod != nil && req.Spec.ExpirationSeconds == token.WarnOnlyBoundTokenExpirationSeconds && r.isKubeAudiences(req.Spec.Audiences)`, es decir, sólo tokens pod-bound con exactamente 3607 s (`WarnOnlyBoundTokenExpirationSeconds = 60*60 + 7`) y audiencia del apiserver; entonces `exp = r.maxExtendedExpirationSeconds` (por defecto `ExpirationExtensionSeconds = 24*365*60*60`) — [token.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/registry/core/serviceaccount/storage/token.go), [claims.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/serviceaccount/claims.go), [options/authentication.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/kubeapiserver/options/authentication.go)
- Uso de un token extendido más allá de su `warnafter` genera la anotación de auditoría `authentication.k8s.io/stale-token` con valor `subject: %s, seconds after warning threshold: %d` y la métrica `serviceaccount_stale_tokens_total` — [claims.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/serviceaccount/claims.go); ejemplo en EKS: `subject: system:serviceaccount:common:fluent-bit, seconds after warning threshold: 4185802.` — [EKS service accounts](https://docs.aws.amazon.com/eks/latest/userguide/service-accounts.html)
- EKS: "Service account tokens have an expiration of one hour... For Amazon EKS clusters, the extended expiry period is 90 days. Your Amazon EKS cluster's Kubernetes API server rejects requests with tokens that are greater than 90 days old" — [EKS service accounts](https://docs.aws.amazon.com/eks/latest/userguide/service-accounts.html)
- Objetos vinculables (`boundObjectRef`): Pod, Secret ("allows revoking tokens by deleting the Secret"), Node (GA v1.33+), y en v1.37 alpha ValidatingWebhookConfiguration/MutatingWebhookConfiguration (feature gate `APIServerWebhookAuthenticationToken`) — [Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/). `kubectl create token --bound-object-kind`: "Supported kinds are Node, Pod, Secret"; `--bound-object-name`: "The token will expire when the object is deleted"; `--duration`: "The server may return a token with a longer or shorter lifetime" — [kubectl create token](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_create/kubectl_create_token/)
- Tokens vinculados a webhooks: la caducidad se recorta a `maxAdmissionReviewWebhookTokenExpirationSeconds` (600 s) y `audiences` debe tener longitud 1 — [token.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/registry/core/serviceaccount/storage/token.go), [validation.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/apis/authentication/validation/validation.go)
- Invalidación: un bound token deja de ser válido cuando el objeto referenciado (Pod, Secret o Node) se elimina, cuando se elimina el ServiceAccount, cuando el `metadata.uid` ya no coincide, o "60+ seconds after `.metadata.deletionTimestamp`" para objetos pendientes de borrado — [Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/). En código: UID del SA distinto → `service account UID (%s) does not match claim`; `DeletionTimestamp` anterior a `invalidIfDeletedBefore := nowTime.Add(-jwt.DefaultLeeway)` → `service account %s/%s has been deleted`; Secret/Pod/Node no encontrado → `service account token has been invalidated` — [claims.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/serviceaccount/claims.go)
- El getter que usa el autenticador consulta primero el lister del informer y, si falla, hace un `Get` en vivo contra la API (`GetServiceAccount`, `GetPod`, `GetSecret`, `GetNode`) — [tokengetter.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/controller/serviceaccount/tokengetter.go)
- Caché de autenticación de tokens en el apiserver: `TokenSuccessCacheTTL: 10 * time.Second`, `TokenFailureCacheTTL: 0` — [options/authentication.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/kubeapiserver/options/authentication.go); la unión de autenticadores de token se envuelve con `tokencache.New(tokenAuth, true, config.TokenSuccessCacheTTL, config.TokenFailureCacheTTL)` — [authenticator/config.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/kubeapiserver/authenticator/config.go)
- Claim `jti`: generado con `uuid.NewString` — [claims.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/serviceaccount/claims.go); se expone en `user.extra` bajo `CredentialIDKey = "authentication.kubernetes.io/credential-id"` — [user.go](https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apiserver/pkg/authentication/user/user.go) — con formato `"JTI=" + jti` (`func CredentialIDForJTI`) — [jwt.go](https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apiserver/pkg/authentication/token/jwt/jwt.go). Ejemplo de TokenReview en la doc: `authentication.kubernetes.io/credential-id: - JTI=7ee52be0-9045-4653-aa5e-0da57b8dccdc` junto a `node-name` y `pod-name` — [Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/)
- En el evento de auditoría de la *emisión* (create de `serviceaccounts/token`) se añade la anotación `authentication.kubernetes.io/issued-credential-id` con `CredentialIDForJTI(sc.ID)` — [token.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/registry/core/serviceaccount/storage/token.go); renombrada desde `credential-id` en v1.30 (PR #123098) — [CHANGELOG-1.30](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.30.md)
- Versiones: `ServiceAccountTokenJTI` alpha 1.29, beta 1.30, GA 1.32; `ServiceAccountTokenPodNodeInfo` alpha 1.29, beta 1.30, GA 1.32; `ServiceAccountTokenNodeBindingValidation` alpha 1.29, beta 1.30, GA 1.32; `ServiceAccountTokenNodeBinding` alpha 1.29, beta 1.31, GA 1.33 (locked) — [feature gate ServiceAccountTokenJTI](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/ServiceAccountTokenJTI.md), [ServiceAccountTokenNodeBinding](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/ServiceAccountTokenNodeBinding.md); coincide con la tabla del KEP — [KEP-4193](https://github.com/kubernetes/enhancements/blob/master/keps/sig-auth/4193-bound-service-account-token-improvements/README.md); CHANGELOG 1.32: "Promoted the `ServiceAccountTokenJTI` feature to GA, which adds a `jti` claim... and embeds the `jti` claim as a `authentication.kubernetes.io/credential-id=["JTI=..."]` value in user extra info" — [CHANGELOG-1.32](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.32.md)
- KEP-4193 describe el JTI como "a UUID which can be later used to trace the requests that a specific issued token has made to the apiserver via the audit log" — [KEP-4193](https://github.com/kubernetes/enhancements/blob/master/keps/sig-auth/4193-bound-service-account-token-improvements/README.md)
- Extras adicionales en tokens pod-bound (GA 1.32): `authentication.kubernetes.io/pod-name`, `pod-uid`, `node-name`, `node-uid` — [Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/)
- Audiencias: `--api-audiences` "If the --service-account-issuer flag is configured and this flag is not, this field defaults to a single element list containing the issuer URL" — [kube-apiserver reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/); `kubectl create token --audience` "If unset, defaults to requesting a token for use with the Kubernetes API server. May be repeated" — [kubectl create token](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_create/kubectl_create_token/)
- `ServiceAccountNodeAudienceRestriction` (restricción de audiencias para tokens pedidos por nodos): beta 1.32 (default false), beta 1.33 (default true) — [feature gate](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/ServiceAccountNodeAudienceRestriction.md)
- SelfSubjectReview (`kubectl auth whoami`) estable desde v1.28 permite al cliente ver su identidad mapeada — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)

### Inferences
- Patrón para la app: un ServiceAccount por desarrollador (o por credencial) + un Secret "ancla" por credencial + `TokenRequest` con `boundObjectRef{kind: Secret}`; borrar el Secret revoca la credencial en ≤ ~10 s (caché de éxito) más la propagación del informer; borrar el SA revoca todas sus credenciales. El token no necesita guardarse en el Secret: el Secret es sólo el ancla de revocación.
- En clústeres sin `--service-account-max-token-expiration` (kubeadm no lo fija por defecto según la ausencia de default en la referencia) un usuario con permiso `create serviceaccounts/token` puede pedir tokens de hasta 2^32 s; la app debe imponer su propio máximo y/o el operador fijar el flag en self-managed. En clústeres gestionados no se puede fijar (ver gaps).
- Los tokens emitidos por la app nunca reciben la extensión a 1 año/90 días (sólo aplica a tokens pod-bound de 3607 s con audiencia kube), así que `exp` es exactamente lo pedido/recortado.
- Atribución en audit: `user.username = system:serviceaccount:<ns>:<sa>`, `user.uid = <uid del SA>`, `user.extra["authentication.kubernetes.io/credential-id"][0] = "JTI=<uuid>"`; el evento de emisión lleva `annotations["authentication.kubernetes.io/issued-credential-id"]`, así que se puede correlacionar emisión → uso sin almacenar el token.
- La revocación efectiva depende de que el apiserver pueda leer el objeto ancla: si la app usa un Secret en un namespace dedicado, los RBAC de los desarrolladores no deben permitirles borrar/recrear ese Secret (recrear con otro UID también invalida, porque el UID va en el token).

### Gaps
- No encontré documentación oficial de EKS, GKE ni AKS sobre el valor de `--service-account-max-token-expiration` en sus control planes, ni si limitan `kubectl create token --duration`; la doc de EKS sólo habla de 1 h + extensión de 90 días para tokens inyectados. Hay que verificarlo empíricamente por proveedor (pedir p. ej. `--duration=8760h` y comprobar el warning "shortened").
- No verifiqué si existe hoy en `master` una validación de rango para `--service-account-max-token-expiration` (mi grep de "must be between" en `options/authentication.go` no devolvió nada); la extracción de ese fichero tampoco encontró un mínimo.
- El valor de `jwt.DefaultLeeway` (la doc dice 60 s) no lo verifiqué en la librería go-jose; me apoyo en la doc oficial.

## 2. Secrets legacy de token de ServiceAccount (larga duración)

### Takeaway
Los Secrets `kubernetes.io/service-account-token` ya no se autogeneran desde v1.24, los no usados se invalidan y borran por el controlador de limpieza (GA en v1.30), pero crearlos manualmente sigue soportado y documentado para sistemas externos/CI; no caducan, se revocan borrando el Secret y cada uso queda anotado en audit con el nombre del Secret (`authentication.k8s.io/legacy-token-manual-secret`), aunque sin `jti`.

### Cited Findings
- La autogeneración de tokens de larga duración se detuvo en v1.24; los existentes siguen funcionando — [Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/). Feature gate `LegacyServiceAccountTokenNoAutoGeneration`: beta 1.24–1.25, GA 1.26–1.28, eliminado — [feature gate](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/LegacyServiceAccountTokenNoAutoGeneration.md)
- `LegacyServiceAccountTokenTracking`: alpha 1.26, beta 1.27, GA 1.28 (eliminado tras 1.29) — [feature gate](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/LegacyServiceAccountTokenTracking.md)
- `LegacyServiceAccountTokenCleanUp`: alpha 1.28, beta 1.29, GA 1.30 (eliminado tras 1.31) — [feature gate](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/LegacyServiceAccountTokenCleanUp.md). (La extracción automática de la página de SA decía "Beta in v1.25+"; es un error de extracción, la fuente autoritativa es el fichero del feature gate.)
- Etiquetas: `LastUsedLabelKey = "kubernetes.io/legacy-token-last-used"`, `InvalidSinceLabelKey = "kubernetes.io/legacy-token-invalid-since"`; si el Secret tiene la etiqueta invalid-since el apiserver rechaza con "the token in secret %s/%s for service account %s/%s has been marked invalid. Use tokens from the TokenRequest API or manually created secret-based tokens, or remove the '%s' label from the secret to temporarily allow use of this token" y anota `authentication.k8s.io/legacy-token-invalidated` — [legacy.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/serviceaccount/legacy.go)
- Anotaciones de auditoría por uso: `authentication.k8s.io/legacy-token` (valor: subject) cuando el token no tiene audiencias — [jwt.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/serviceaccount/jwt.go); `authentication.k8s.io/legacy-token-autogenerated-secret` (con warning "Use tokens from the TokenRequest API or manually created secret-based tokens instead of auto-generated secret-based tokens.") y `authentication.k8s.io/legacy-token-manual-secret` (valor: nombre del Secret) para los creados a mano; cada uso actualiza la etiqueta last-used (`patchSecretWithLastUsedDate`) — [legacy.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/serviceaccount/legacy.go)
- Creación manual: Secret `type: kubernetes.io/service-account-token` con anotación `kubernetes.io/service-account.name`; casos recomendados: sistemas externos, CI/CD, cuando el token debe sobrevivir a varios ciclos de vida de workloads — [Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/)
- Los tokens vinculados a un Secret vía TokenRequest se invalidan al borrar el Secret (alternativa moderna) — [Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/)

### Inferences
- Para CI, un Secret legacy sigue siendo "aceptable" sólo si se necesita una credencial sin caducidad y no se puede renovar; la alternativa equivalente y más segura es un token TokenRequest de larga duración vinculado a un Secret (mismo mecanismo de revocación, con `exp` y `jti`).
- Atribución: los tokens legacy no llevan `credential-id`, pero la anotación `legacy-token-manual-secret: <nombre>` los hace atribuibles al Secret (una credencial = un Secret). El `LegacyServiceAccountTokenCleanUp` sólo afecta a Secrets *no usados*; un Secret usado periódicamente por CI no se invalida.
- Funcionan igual en EKS/GKE/AKS/self-managed porque dependen del token-controller del kube-controller-manager, no de flags del apiserver (no encontré ninguna restricción documentada por proveedor).

### Gaps
- No verifiqué el valor por defecto del periodo de limpieza del kube-controller-manager (`--legacy-service-account-token-clean-up-period`; la doc sólo dice "configurable").

## 3. Certificados X.509 vía CertificateSigningRequest (`kubernetes.io/kube-apiserver-client`)

### Takeaway
Kubernetes sigue sin soportar revocación de certificados de cliente (ni CRL ni OCSP; issues abiertos desde 2018/2019 y ningún KEP en 2025-2026 lo cambia): un certificado vale hasta `notAfter`, con vida = min(`--cluster-signing-duration`, `spec.expirationSeconds` ≥ 600 s). Desde v1.32 cada petición autenticada por certificado lleva `credential-id = X509SHA256=<sha256 del DER>` y desde v1.33/1.34 puede llevar un `uid` embebido (OID `1.3.6.1.4.1.57683.2`). En EKS los CSR con `client auth` se aprueban pero no se emiten; en GKE el signer funciona a través de CA Service; en AKS no hay documentación oficial.

### Cited Findings
- "Kubernetes {{< skew currentVersion >}} does not support certificate _revocation_. Any certificate that is issued remains valid until it expires." — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- Issues abiertos: "Support client certificate revocation" #60917 y "TOB-K8S-028: Kubernetes does not facilitate certificate revocation" #81111 (hallazgo de la auditoría de Trail of Bits) — [kubernetes#60917](https://github.com/kubernetes/kubernetes/issues/60917), [kubernetes#81111](https://github.com/kubernetes/kubernetes/issues/81111)
- Reglas del signer `kubernetes.io/kube-apiserver-client`: "Never auto-approved by kube-controller-manager"; trust distribution: "signed certificates must be honored as client certificates by the API server"; "Permitted key usages - must include ["client auth"]. Must not include key usages beyond ["digital signature", "key encipherment", "client auth"]"; "Expiration/certificate lifetime - ... set to the minimum of the `--cluster-signing-duration` option or, if specified, the `spec.expirationSeconds` field"; "CA bit allowed/disallowed - not allowed"; el admission plugin `CertificateSubjectRestriction` bloquea `system:masters` por defecto — [Certificate Signing Requests](https://kubernetes.io/docs/reference/access-authn-authz/certificate-signing-requests/)
- `spec.expirationSeconds`: mínimo 600 (10 min), opcional desde v1.22; feature gate `CSRDuration` beta 1.22–1.23, GA 1.24–1.25, eliminado — [Certificate Signing Requests](https://kubernetes.io/docs/reference/access-authn-authz/certificate-signing-requests/), [feature gate CSRDuration](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/CSRDuration.md)
- `--cluster-signing-duration`: "The max length of duration signed certificates will be given. Individual CSRs may request shorter certs by setting spec.expirationSeconds." — [kube-controller-manager reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-controller-manager/)
- Recolección automática de CSRs: aprobados/denegados/fallidos tras 1 h, pendientes tras 24 h, todos tras la caducidad del certificado — [Certificate Signing Requests](https://kubernetes.io/docs/reference/access-authn-authz/certificate-signing-requests/)
- RBAC para aprobar: `certificatesigningrequests/approval` verb `update` + `signers` verb `approve` con `resourceNames`; para firmar: `certificatesigningrequests/status` `update` + `signers` verb `sign` — [Certificate Signing Requests](https://kubernetes.io/docs/reference/access-authn-authz/certificate-signing-requests/)
- Credential ID para certificados: `fp := sha256.Sum256(chain[0].Raw); id := "X509SHA256=" + hex.EncodeToString(fp[:])` y se añade a `Extra: {user.CredentialIDKey: {id}}` (misma clave `authentication.kubernetes.io/credential-id`) — [x509.go](https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apiserver/pkg/authentication/request/x509/x509.go); CHANGELOG 1.32: "X.509 client certificate authentication to the kube-apiserver now produces credential IDs (derived from the certificate's signature), for use in audit logging" (PR #125634) — [CHANGELOG-1.32](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.32.md)
- GKE documenta la clave como `"authentication.k8s.io/credential-id": "X509SHA256=CERTIFICATE_HASH"` para certificados y `"authentication.kubernetes.io/credential-id": "JTI=JWT_ID"` para JWT, y exige "GKE version 1.31.1-gke.1846000 or later"; en Cloud Logging aparecen en `labels."authentication.kubernetes.io/credential-id"` — [GKE: Verify identity issuance and usage](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/verify-identity-issuance-usage). (Discrepancia: el código upstream usa `authentication.kubernetes.io/credential-id` para ambos; la clave `authentication.k8s.io/...` de la doc de GKE parece una errata o un mapeo propio de GKE.)
- UID desde certificado: atributo OID `1.3.6.1.4.1.57683.2` en el subject; feature gate `AllowParsingUserUIDFromCertAuth` alpha 1.33, beta 1.34 (default true) — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/), [feature gate](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/AllowParsingUserUIDFromCertAuth.md)
- Username = `commonName`, grupos = campos `organization` del subject; se activa con `--client-ca-file` — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- EKS: para el signer propio `beta.eks.amazonaws.com/app-serving` "Permitted key usages: Must not include usages beyond ["key encipherment", "digital signature", "server auth"]... Note: Client certificate signing is not supported... Expiration/certificate lifetime: 45 days (default and maximum)"; `kubernetes.io/legacy-unknown` no se acepta en `certificates.k8s.io/v1` — [EKS cert-signing](https://docs.aws.amazon.com/eks/latest/userguide/cert-signing.html). Issue de roadmap (abierto desde 2022-10-10, etiqueta "Proposed", sin respuesta de AWS): con usage `client auth` el CSR "gets approved but no certificate is issued... regardless of which signerName is used—either `kubernetes.io/kube-apiserver-client` or `beta.eks.amazonaws.com/app-serving`" — [aws/containers-roadmap#1856](https://github.com/aws/containers-roadmap/issues/1856)
- GKE: "Client certificate issuance: disabled by default on clusters running GKE version 1.12 and later"; basic auth eliminado en 1.19; la certificates API "cannot be disabled" y "is used to operate the cluster" — [GKE: Authenticate to the Kubernetes API server](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/api-server-authentication); "To issue certificates, the Kubernetes control plane sends an approved CertificateSigningRequest to a certificate authority (CA) in CA Service" — [GKE: Verify identity issuance and usage](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/verify-identity-issuance-usage)
- AKS: las "local accounts" son "a built-in cluster admin certificate that bypasses Entra ID"; "`--admin` access still exists as a non-auditable backdoor option"; tras deshabilitarlas "the administrator must rotate the cluster certificates to revoke certificates they might have had access to" — [AKS local accounts](https://learn.microsoft.com/en-us/azure/aks/local-accounts), [AKS cluster authentication concepts](https://learn.microsoft.com/en-us/azure/aks/concepts-cluster-authentication)
- Pod certificates (KEP-4317) y ClusterTrustBundle (KEP-3257) pasan a Stable en v1.37 — [Kubernetes v1.37 release](https://kubernetes.io/blog/2026/08/26/kubernetes-v1-37-release/); `PodCertificateRequest` alpha 1.34, beta 1.35–1.36 (default false), GA 1.37; `ClusterTrustBundle` alpha 1.27–1.32, beta 1.33–1.36 (default false), GA 1.37 — [feature gate PodCertificateRequest](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/PodCertificateRequest.md), [feature gate ClusterTrustBundle](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/ClusterTrustBundle.md)

### Inferences
- Ningún cambio en 1.35–1.37 introduce revocación de certificados de cliente: los greps de los blogs de release y de los CHANGELOG no muestran nada al respecto y las únicas novedades X.509 (Pod certificates, ClusterTrustBundle) son para workloads.
- La única "revocación" posible es (a) certificados muy cortos (mínimo 10 min) o (b) revocar en la capa de autorización (borrar RoleBindings del CN/UID; el usuario sigue autenticándose pero sin permisos), o (c) rotar la CA de cliente (impacto global).
- Con `AllowParsingUserUIDFromCertAuth` (beta, on por defecto desde 1.34) la app podría embeber un ID de credencial como `uid` del certificado y obtener atribución por `user.uid` además del `X509SHA256`. Pero para 1.32 ≤ versión < 1.33 sólo hay `X509SHA256`.
- Portabilidad: EKS = no usable para credenciales de usuario (CSR no emitido); GKE = usable (signer implementado vía CA Service; cluster-level "client certificate" es otra cosa); AKS = sin confirmación oficial; self-managed = usable si kube-controller-manager tiene `--cluster-signing-cert-file/--cluster-signing-key-file` (kubeadm lo configura por defecto: no verificado en esta investigación).

### Gaps
- El valor por defecto de `--cluster-signing-duration` no se capturó en la extracción (de memoria es 8760h0m0s = 1 año; verificar en la referencia del kube-controller-manager).
- No encontré documentación oficial de AKS que confirme o niegue que el signer `kubernetes.io/kube-apiserver-client` emita certificados.
- No hay respuesta oficial de AWS en el issue #1856; el comportamiento "approved but never issued" viene del reporte comunitario y de la doc EKS del signer propio.

## 4. OIDC: flags `--oidc-*` vs Structured Authentication Configuration

### Takeaway
La Structured Authentication Configuration (`--authentication-config`, `AuthenticationConfiguration`) es GA desde v1.34 con `apiVersion: apiserver.config.k8s.io/v1`, hasta 64 issuers, CEL en `claimValidationRules`/`claimMappings`/`userValidationRules`, recarga dinámica y (desde 1.32) `credential-id = JTI=<jti>` si el token trae `jti`; los flags `--oidc-*` siguen soportados y no están formalmente deprecados, pero son mutuamente excluyentes con el fichero. En gestionados: EKS expone sólo el modelo "clásico" (hasta 10 providers en ≥1.32, sin CEL), GKE no permite BYO OIDC en el apiserver (Identity Service for GKE deprecado el 1-jul-2026, sustituido por Workforce Identity Federation) y AKS ofrece structured authentication con providers externos en *preview*.

### Cited Findings
- Flags clásicos: `--oidc-issuer-url` ("The URL scheme **must** be `https`"), `--oidc-client-id`, `--oidc-username-claim` (default `sub`), `--oidc-username-prefix` (default `( Issuer URL )#` si el claim no es `email`; `-` desactiva), `--oidc-groups-claim` (array de strings), `--oidc-groups-prefix`, `--oidc-required-claim` (`key=value`, repetible), `--oidc-ca-file`, `--oidc-signing-algs` (Default "RS256" en la referencia v1.37) — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/), [kube-apiserver reference (v1.37)](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/)
- Ni la referencia de flags v1.37 ni el texto de ayuda en el código marcan los `--oidc-*` como deprecated — [kube-apiserver reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/), [options/authentication.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/kubeapiserver/options/authentication.go). El KEP no fija un calendario de deprecación; sólo indica que `--oidc-signing-algs` se eliminará porque "provides no benefit" — [KEP-3331](https://github.com/kubernetes/enhancements/blob/master/keps/sig-auth/3331-structured-authentication-configuration/README.md)
- Exclusión mutua: `--authentication-config` "is mutually exclusive with the --oidc-* flags if the file configures the JWT Token authenticator... mutually exclusive with --anonymous-auth if the file configures the Anonymous authenticator" — [kube-apiserver reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/); "If you specify `--authentication-config` along with any of the `--oidc-*` command line arguments, this is a misconfiguration. In this situation, the API server reports an error and then immediately exits." — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/); error de validación en código: "authentication-config file and oidc-* flags are mutually exclusive" — [options/authentication.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/kubeapiserver/options/authentication.go)
- Versiones del feature gate `StructuredAuthenticationConfiguration`: alpha 1.29, beta 1.30–1.33, GA 1.34 (locked) — [feature gate](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/StructuredAuthenticationConfiguration.md); CHANGELOG 1.34: "Promoted the `StructuredAuthenticationConfiguration` feature gate to GA" (#131916) y "the AuthenticationConfiguration type accepted in `--authentication-config` files has been promoted to `apiserver.config.k8s.io/v1`" (#131752) — [CHANGELOG-1.34](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.34.md)
- Capacidades documentadas: "multiple JWT authenticators, each with a unique `issuer.url` and `issuer.discoveryURL`"; CEL para mapear y validar; recarga automática al modificar el fichero con métrica `apiserver_authentication_config_controller_automatic_reload_last_timestamp_seconds`; "the maximum number of allowed authenticators is 64"; `issuer.url` "must not conflict with issuer configured in --service-account-issuer"; `discoveryURL` (debe incluir `/.well-known/openid-configuration` y el `issuer` del documento debe coincidir con `issuer.url`); `certificateAuthority` (PEM inline); `audiences` + `audienceMatchPolicy: MatchAny` (obligatorio con varias audiencias); `claimValidationRules` con `claim`/`requiredValue` o `expression`/`message` (ej. `claims.exp - claims.nbf <= 86400`, "total token lifetime must not exceed 24 hours"); `claimMappings.username` (`claim`+`prefix` obligatorio, o `expression`; si se usa `claims.email` hay que usar `claims.email_verified`), `groups`, `uid`, `extra[].key/valueExpression` (clave con prefijo de dominio, minúsculas, única); `userValidationRules` con variable `user` (ej. `!user.username.startsWith('system:')`) — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- `egressSelectorType` (`controlplane` | `cluster`) en `jwt[].issuer`: feature gate `StructuredAuthenticationConfigurationEgressSelector` beta 1.34 (default true) — [feature gate](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/StructuredAuthenticationConfigurationEgressSelector.md), [CHANGELOG-1.34](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.34.md)
- Limitación documentada: "Distributed claims do not work via CEL expressions" — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/). Limitaciones del KEP: sólo algoritmos asimétricos, HTTPS obligatorio, sin `x5c`, sin acceso a la cabecera JWT desde CEL, sin JWT multi-firma, y "Administrators must ensure tokens are short-lived due to lack of revocation support"; el KEP menciona usar el `jti` contra una denylist en `userValidationRules` para simular revocación — [KEP-3331](https://github.com/kubernetes/enhancements/blob/master/keps/sig-auth/3331-structured-authentication-configuration/README.md)
- Credential ID en OIDC/JWT: "JWT authenticators now set the `jti` claim (if present and is a string value) as credential id for use by audit logging" (PR #127010, v1.32) — [CHANGELOG-1.32](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.32.md); en código `getCredentialID` devuelve `CredentialIDForJTI(jti)` y lo mete en `extra[user.CredentialIDKey]` — [oidc.go](https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apiserver/plugin/pkg/authenticator/token/oidc/oidc.go)
- Anonymous authenticator configurable por endpoint (`anonymous.conditions[].path`): `AnonymousAuthConfigurableEndpoints` alpha 1.31, beta 1.32–1.33, GA 1.34 (locked) — [feature gate](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/AnonymousAuthConfigurableEndpoints.md)
- EKS: "On clusters running Kubernetes version 1.32 or later, you can associate up to 10 OIDC identity providers. The combined size of all OIDC provider configurations must be less than 12 KB. On clusters running a version earlier than 1.32, you can associate only one"; "The issuer URL of the OIDC identity provider must be publicly accessible... Amazon EKS doesn't support OIDC identity providers with self-signed certificates"; "You can't disable IAM authentication"; campos: `issuerUrl`, `clientId`, `usernameClaim`, `usernamePrefix`, `groupsClaim`, `groupsPrefix`, `requiredClaims`; "Don't specify `system:`... for `groupsPrefix` or `usernamePrefix`"; "Associating an OIDC identity provider is a cluster update... can take several minutes"; "OIDC identity provider-authenticated users are listed in the cluster's audit log if CloudWatch logs are turned on for the control plane" — [EKS: external OIDC provider](https://docs.aws.amazon.com/eks/latest/userguide/authenticate-oidc-identity-provider.html)
- GKE: "Starting on July 1, 2026, Identity Service for GKE is deprecated and is unsupported in GKE version 1.37 and later"; funciona con componentes en el clúster: `gke-oidc-envoy` "a proxy for the Kubernetes API server, and impersonates users when passing on requests to the API server", `gke-oidc-service` valida tokens; sólo Standard (no Autopilot); el sustituto recomendado es Workforce Identity Federation ("doesn't require any in-cluster installation, works with Autopilot clusters and Standard clusters") — [GKE: external identity providers](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/oidc), [Workforce Identity Federation](https://docs.cloud.google.com/iam/docs/workforce-identity-federation). Métodos soportados por el apiserver de GKE: OAuth con identidades Google (gcloud), tokens de ServiceAccount, cuentas de servicio IAM, y certificados/basic auth como legacy — [GKE: Authenticate to the API server](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/api-server-authentication)
- AKS: "AKS supports structured authentication, which allows you to configure external identity providers... based on the upstream Kubernetes structured authentication configuration... through JSON Web Token (JWT) authenticators"; permite "multiple identity providers simultaneously on a single cluster", `claimValidationRules`/`claimMappings`/`userValidationRules` con CEL; "All usernames and groups mapped through structured authentication must be prefixed with `aks:jwt:`"; "Microsoft Entra ID isn't supported as an external identity provider through structured authentication"; el IdP debe tener "publicly accessible OIDC discovery endpoints"; estado *Preview* ("aren't meant for production use"), doc fechada 2026-01-26 — [AKS: external identity providers (Preview)](https://learn.microsoft.com/en-us/azure/aks/external-identity-provider-authentication-overview); "AKS supports this through structured authentication, which configures the Kubernetes API server's JWT authenticators" — [AKS cluster authentication concepts](https://learn.microsoft.com/en-us/azure/aks/concepts-cluster-authentication)
- AKS Entra: "the cluster validates incoming Kubernetes API requests against Microsoft Entra ID"; "The Microsoft Entra tenant configured for cluster authentication must be the same as the tenant of the subscription"; "For non-interactive logins or older `kubectl` versions, use the `kubelogin` plugin" — [AKS cluster authentication concepts](https://learn.microsoft.com/en-us/azure/aks/concepts-cluster-authentication)

### Inferences
- Self-managed: se puede usar directamente el fichero `AuthenticationConfiguration` (kubeadm `apiServer.extraArgs` + `extraVolumes`, k3s/RKE2 `--kube-apiserver-arg`, Talos `cluster.apiServer.extraArgs/extraVolumes`; ver sección 8). Con `claimMappings.extra` la app podría propagar un ID de sesión/credencial propio a `user.extra` y con `userValidationRules` + recarga dinámica implementar una denylist por `jti` (recarga ~1 min según el KEP).
- EKS no expone CEL ni `extra`; la atribución por credencial OIDC en EKS depende de que el IdP emita `jti` (el apiserver 1.32+ lo mapeará a `credential-id` porque el authenticator es el mismo código upstream) — esto último es inferencia: EKS no lo documenta.
- GKE: para un IdP externo hay que ir por Workforce Identity Federation (identidad IAM de Google, no OIDC directo al apiserver); el audit de GKE mostrará el principal federado. Identity Service for GKE producía peticiones *impersonadas* por `gke-oidc-envoy`, lo que cambia la forma de auditar.
- AKS: la vía externa es la más fiel al upstream (CEL, varios issuers) pero está en preview; la vía Entra es GA. En ambos casos no hay acceso a flags.

### Gaps
- No encontré documentación de EKS sobre si su implementación mapea `jti` a `credential-id` ni sobre cómo se representan los `extra` de OIDC en CloudWatch.
- No verifiqué qué versión mínima de Kubernetes/AKS requiere el preview de external identity providers ni si expone `claimMappings.extra`.
- No encontré fecha prevista para la eliminación de los flags `--oidc-*`.

## 5. Firma externa de tokens de ServiceAccount (KEP-740, ExternalJWTSigner)

### Takeaway
GA en v1.36: `--service-account-signing-endpoint` (socket Unix, gRPC `ExternalJWTSigner` con `Sign`/`FetchKeys`/`Metadata`) sustituye a los ficheros de clave para firmar tokens de SA con un KMS/HSM y rotar claves sin reiniciar; no es un mecanismo de credenciales de usuario y sólo es configurable en self-managed, por lo que su relevancia para la app es marginal (endurecer la firma de los tokens que emite).

### Cited Findings
- Feature gate `ExternalServiceAccountTokenSigner`: alpha 1.32–1.33, beta 1.34–1.35, GA 1.36 — [feature gate](https://github.com/kubernetes/website/blob/main/content/en/docs/reference/command-line-tools-reference/feature-gates/ExternalServiceAccountTokenSigner.md); "In Kubernetes v1.36, the _external ServiceAccount token signer_ feature for service accounts graduates to stable... including support for extended expiration when needed... The kube-apiserver is wired to discover public keys from the external signer, cache them, and validate tokens it did not sign itself" — [Kubernetes v1.36 release](https://kubernetes.io/blog/2026/04/22/kubernetes-v1-36-release/)
- `--service-account-signing-endpoint` "Path to socket where an external JWT signer is listening" — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/); mutuamente excluyente con `--service-account-signing-key-file`/`--service-account-key-file` ("shall result in an error"); servicio gRPC `ExternalJWTSigner` con `Sign()`, `FetchKeys()`, `Metadata()`; transporte Unix domain socket; propósito "integration with HSMs and cloud KMSes" y rotación sin reinicio; "the gRPC overhead adds about 1ms to a TokenRequest"; el signer queda "in the critical path of kube-apiserver" — [KEP-740](https://github.com/kubernetes/enhancements/blob/master/keps/sig-auth/740-service-account-external-signing/README.md)
- 1.34 corrigió la publicación del discovery document OIDC con firma externa activada (#131493) — [CHANGELOG-1.34](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.34.md)

### Inferences
- Para la app: irrelevante en EKS/GKE/AKS (no se controla el apiserver); en self-managed puede interesar si se exige que la clave de firma de los tokens de desarrollador viva en un HSM/KMS y se rote; no cambia formato ni claims (`jti`, `exp`, bound refs) de los tokens emitidos.

### Gaps
- No encontré documentación de ningún proveedor gestionado que exponga o mencione el uso interno de ExternalJWTSigner.

## 6. Impersonation de usuarios

### Takeaway
Impersonation usa las cabeceras `Impersonate-User/Group/Uid/Extra-*` y exige el verbo `impersonate` sobre `users`, `groups`, `serviceaccounts` (core) y `uids`, `userextras/<clave>` (`authentication.k8s.io`); es cluster-scoped para usuarios/grupos (ClusterRole+ClusterRoleBinding) y namespace-scoped para ServiceAccounts; el audit log registra al impersonador en `user` y al suplantado en `impersonatedUser`. Desde v1.35 (alpha) / v1.36 (beta, on por defecto) existe *Constrained Impersonation* (KEP-5284) con verbos `impersonate:user-info`, `impersonate:serviceaccount`, `impersonate:(arbitrary|associated)-node` e `impersonate-on:<modo>:<verbo>` que limita qué acciones puede realizar el impersonador.

### Cited Findings
- Cabeceras: `Impersonate-User` (obligatoria), `Impersonate-Uid` (opcional, requiere `Impersonate-User`, "available in v1.22.0+"), `Impersonate-Group` (repetible), `Impersonate-Extra-( extra name )` (clave en minúsculas y percent-encoded) — [User impersonation](https://kubernetes.io/docs/reference/access-authn-authz/user-impersonation/)
- RBAC: ClusterRole con `apiGroups: [""]`, `resources: ["users","groups","serviceaccounts"]`, `verbs: ["impersonate"]`; para extras y UIDs `apiGroups: ["authentication.k8s.io"]`, `resources: ["userextras/scopes","uids"]`; se puede restringir con `resourceNames` (usuario concreto, grupos concretos, valores concretos de extra, UID concreto) — [User impersonation](https://kubernetes.io/docs/reference/access-authn-authz/user-impersonation/)
- "Impersonating a user or group allows you to perform any action as if you were that user or group; for that reason, impersonation is not namespace scoped... this requires using a ClusterRole and a ClusterRoleBinding, not a Role and RoleBinding. Granting impersonation over ServiceAccounts is namespace scoped, but the impersonated ServiceAccount could perform actions outside of namespace." — [User impersonation](https://kubernetes.io/docs/reference/access-authn-authz/user-impersonation/)
- Al impersonar un ServiceAccount se añaden automáticamente los grupos `system:serviceaccounts` y `system:serviceaccounts:<namespace>`; el grupo `system:authenticated` se añade automáticamente; las peticiones impersonadas se registran con el campo `impersonatedUser` en el audit log — [User impersonation](https://kubernetes.io/docs/reference/access-authn-authz/user-impersonation/); el Event de auditoría incluye `user` (username/uid/groups/extra) e `impersonatedUser` — [Auditing](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/)
- kubectl: `--as`, `--as-group` (repetible), `--as-uid` (v1.23+), `--as-user-extra=<key>=<value>` (v1.35+, PR #134378) — [User impersonation](https://kubernetes.io/docs/reference/access-authn-authz/user-impersonation/), [CHANGELOG-1.35](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.35.md)
- Constrained Impersonation (KEP-5284): implementado en v1.35 (PR #134803, alpha) y "Promoted the `ConstrainedImpersonation` feature to beta, enabled by default" en v1.36 (#137609); añade la anotación de auditoría `apiserver.latency.k8s.io/impersonation` para peticiones lentas y métricas `apiserver_impersonation_attempts_total{mode, decision}` etc. — [CHANGELOG-1.35](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.35.md), [CHANGELOG-1.36](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.36.md), [Kubernetes v1.36 release](https://kubernetes.io/blog/2026/04/22/kubernetes-v1-36-release/)
- Modos y verbos (todos en `authentication.k8s.io`): user-info (usernames que no empiezan por `system:serviceaccount:` ni `system:node:`): `impersonate:user-info`, `impersonate-on:user-info:<verb>`; serviceaccount: `impersonate:serviceaccount`, `impersonate-on:serviceaccount:<verb>` ("For service accounts, you must specify the namespace in the RoleBinding"); node: `impersonate:arbitrary-node`, `impersonate:associated-node`, `impersonate-on:arbitrary-node:<verb>`, `impersonate-on:associated-node:<verb>`; "Constrained impersonation requires two separate permissions"; "Existing impersonate rules keep working, but the API server prefers the new constrained checks first" — [User impersonation](https://kubernetes.io/docs/reference/access-authn-authz/user-impersonation/), [Kubernetes v1.36 release](https://kubernetes.io/blog/2026/04/22/kubernetes-v1-36-release/)
- Anotaciones de autorización en audit: `authorization.k8s.io/decision`, `authorization.k8s.io/reason` — [Auditing](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/)
- El helper de la app de EKS (Identity Service for GKE) usa precisamente impersonation desde un proxy (`gke-oidc-envoy ... impersonates users`) — [GKE: external identity providers](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/oidc)

### Inferences
- Patrón "gateway": la app (o un proxy) se autentica con su propia credencial y suplanta `dev-<nombre>` con `Impersonate-Extra-session-id: <id>`; el audit tendrá `user` = SA del proxy (con su `credential-id`), `impersonatedUser.username/groups/extra` = desarrollador + id de sesión. Requiere que el proxy tenga `impersonate` sobre `users`, `groups` y `userextras/session-id`, y exige que todo el tráfico pase por el proxy (no sirve para kubeconfigs directos).
- Funciona igual en EKS/GKE/AKS/self-managed porque es lógica del apiserver + RBAC (sin flags); en clústeres con Azure RBAC para Kubernetes o EKS access policies hay que comprobar que el autorizador delegado entienda el verbo `impersonate` (gap).
- Con constrained impersonation en beta (1.36+, on por defecto) se puede limitar al proxy a "sólo list/watch pods en ns X en nombre de Y", reduciendo el riesgo de un proxy comprometido.

### Gaps
- No encontré en la doc ninguna restricción específica para impersonar grupos `system:` (p. ej. `system:masters`); el ejemplo oficial usa `--as-group=system:masters`, así que sólo lo limita RBAC (`resourceNames`).
- No verifiqué cómo representan CloudWatch (EKS), Cloud Audit Logs (GKE) y la tabla `AKSAudit` el campo `impersonatedUser` (la tabla AKSAudit documentada no lista una columna ImpersonatedUser).

## 7. Lado cliente: exec credential plugins y herramientas (kubelogin, aws eks get-token, gke-gcloud-auth-plugin, k9s/Lens/Helm)

### Takeaway
Los exec plugins (`client.authentication.k8s.io/v1`, GA v1.22) devuelven un `ExecCredential` con token o cert y opcional `expirationTimestamp` (client-go cachea en memoria hasta ese instante o hasta un 401); `interactiveMode` (`Never`/`IfAvailable`/`Always`, obligatorio en v1) decide si el plugin recibe stdin, lo que rompe flujos interactivos en GUIs como Lens; los plugins de proveedor (aws 15 min sin caché documentada; gcloud ~1 h; Azure kubelogin caché en `~/.kube/cache/kubelogin`; int128 kubelogin caché en `~/.kube/cache/oidc-login` con refresh token) y desde v1.35/1.36 `kuberc` permite allowlist/denylist de plugins.

### Cited Findings
- client-go credential plugins: estable desde v1.22; "Almost all credential plugin use cases require a server side component with support for the webhook token authenticator"; "Earlier versions of `kubectl` included built-in support for authenticating to AKS and GKE, but this is no longer present" — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- `interactiveMode`: `Never` (nunca usa stdin), `IfAvailable` (lo usa si está), `Always` (si no hay stdin "the exec plugin will not be run and an error will be returned"); "optional in `client.authentication.k8s.io/v1beta1` and required in `client.authentication.k8s.io/v1`" — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- Caducidad: "If an expiry is included, the bearer token and TLS credentials are cached until the expiry time is reached, or if the server responds with a 401 HTTP status code, or when the process exits. If an expiry is omitted, ... cached until the server responds with a 401 ... or until the process exits."; `provideClusterInfo: true` entrega la info del clúster en `KUBERNETES_EXEC_INFO` — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- `kuberc` (KEP-3104): "Configurable credential plugin policy in `kuberc`" en beta en v1.35 y en v1.36 "(allowlists or denylists) to enforce safer authentication practicies"; en 1.36 se renombró `AllowlistEntry.Name` a `AllowlistEntry.Command` (#137272) — [Kubernetes v1.35 release](https://kubernetes.io/blog/2025/12/17/kubernetes-v1-35-release/), [Kubernetes v1.36 release](https://kubernetes.io/blog/2026/04/22/kubernetes-v1-36-release/), [CHANGELOG-1.36](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.36.md)

- Lens: issue abierto "Unable to connect to Azure Kubernetes Cluster - devicelogin is not supported if interactiveMode is 'never'" (error `getting credentials: exec: executable kubelogin failed with exit code 1`) — [lensapp/lens#6586](https://github.com/lensapp/lens/issues/6586); otros reportes: OIDC "works fine via command line (kubectl) and via k9s" pero no en Lens — [lensapp/lens#5976](https://github.com/lensapp/lens/issues/5976); `unknown command "oidc-login" for "kubectl"` por PATH — [lensapp/lens#7520](https://github.com/lensapp/lens/issues/7520); "Lens not working correctly when kubelogin auth is used" — [lensapp/lens#6427](https://github.com/lensapp/lens/issues/6427)

### Inferences
- Para una GUI sin TTY (Lens) el plugin debe poder resolver la credencial sin stdin: modos no interactivos (`azurecli`, tokens ya cacheados, o un plugin propio que lea un token de un fichero/keyring) y `interactiveMode: Never|IfAvailable`. k9s y Helm son procesos con TTY que usan client-go, por lo que se comportan como kubectl (no encontré doc específica de k9s/Helm; inferencia a partir de que ambos usan client-go y de los reportes de Lens).
- Un token TokenRequest entregado por la app se puede consumir sin plugin (`users[].user.token`) o con un exec plugin mínimo que lo lea de un almacén local y lo renueve contra la app; el `expirationTimestamp` debe coincidir con `exp` para que client-go no reutilice un token caducado.
- Los tokens de proveedor (IAM 15 min, Google/Entra ~1 h) no son "credenciales emitidas" por la app: la atribución en audit se hace por identidad IAM/Google/Entra (extras `accessKeyId`/`sessionName` en EKS), no por un id de credencial de la app.

### Gaps
- No encontré documentación oficial de k9s ni de Helm sobre exec plugins/interactividad; sólo evidencia indirecta en issues de Lens.
- No verifiqué si `aws eks get-token` implementa caché en versiones recientes de la CLI (la referencia no lo documenta).

## 8. Webhook token authentication, authorization webhooks y Structured Authorization Configuration

### Takeaway
El webhook de autenticación (`--authentication-token-webhook-config-file`, caché 2 min por defecto, `TokenReview` v1beta1 por defecto) y el de autorización (`--authorization-webhook-config-file` o el fichero `AuthorizationConfiguration`, GA en v1.32 con CEL `matchConditions`, `failurePolicy` y recarga) son las bases de EKS (aws-iam-authenticator) y de Azure RBAC, pero como requieren flags del apiserver sólo son BYO en self-managed (kubeadm `extraArgs/extraVolumes`, k3s/RKE2 `--kube-apiserver-arg`, Talos `cluster.apiServer.extraArgs/authorizationConfig`).

### Cited Findings
- Webhook token authentication: `--authentication-token-webhook-config-file` (kubeconfig), `--authentication-token-webhook-cache-ttl` ("Defaults to two minutes"; referencia: Default 2m0s), `--authentication-token-webhook-version` (`v1beta1` por defecto; "To opt into receiving `authentication.k8s.io/v1` token reviews, the API server must be started with `--authentication-token-webhook-version=v1`"); "Changes made to this file while the API server is running are **not** re-read" — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/), [kube-apiserver reference](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/); el autenticador webhook se envuelve en `tokencache.New(webhookTokenAuthenticator, false, config.WebhookTokenAuthnCacheTTL, ...)` — [authenticator/config.go](https://github.com/kubernetes/kubernetes/blob/master/pkg/kubeapiserver/authenticator/config.go)
- Static token file `--token-auth-file`: "Changes made to this file while the API server is running are **not** re-read" — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/); authenticating proxy: `--requestheader-client-ca-file` (obligatorio), `--requestheader-allowed-names`, `--requestheader-username-headers`, `--requestheader-group-headers`, `--requestheader-extra-headers-prefix` — [Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)

- EKS: los eventos de audit llegan a CloudWatch en el stream `kube-apiserver-audit` cuando el control plane logging está habilitado (query de ejemplo con `filter @logStream like /kube-apiserver-audit/`) — [EKS service accounts](https://docs.aws.amazon.com/eks/latest/userguide/service-accounts.html)
- GKE: "Admin Activity logs (always enabled)... Data Access logs (disabled by default): include 'admin read' operations and 'data read/write' operations. Must be explicitly enabled"; servicio `k8s.io`; campos `protoPayload.authenticationInfo.principalEmail`, `protoPayload.methodName`, `protoPayload.requestMetadata.callerIp` — [GKE audit logging](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/audit-logging); credential-id en `labels."authentication.kubernetes.io/credential-id"` — [GKE: Verify identity issuance and usage](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/verify-identity-issuance-usage)
- AKS: tabla `AKSAudit` ("all Kubernetes API Server audit logs including events with the get and list verbs"; `AKSAuditAdmin` para operaciones de modificación; "Requires Diagnostic Settings") con columnas `User` (dynamic: "Authenticated user metadata of the requesting client, including optional fields such as UID and groups"), `Annotations`, `AuditId`, `SourceIps`, `UserAgent`, `Verb`, `ObjectRef`, `RequestUri`, `ResponseStatus`, `Stage`, `Level` — [AKSAudit table](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/aksaudit)

### Inferences
- Un webhook de autenticación propio (p. ej. que valide tokens opacos emitidos por la app y devuelva `user.extra` con un id de credencial) da revocación instantánea (menos `--authentication-token-webhook-cache-ttl`, 2 min por defecto, ajustable) y atribución total, pero sólo en self-managed.
- En clústeres gestionados la política de auditoría no es configurable (EKS/GKE/AKS documentan destinos y tablas, no `--audit-policy-file`); GKE además exige activar Data Access logs para ver lecturas (get/list/watch), imprescindible para "full per-request audit".
- Static token file no sirve para credenciales dinámicas (requiere reinicio del apiserver para añadir/revocar).

### Gaps
- No verifiqué si EKS/GKE/AKS conservan `user.extra` íntegro en sus destinos de log (CloudWatch parece volcar el JSON del Event; GKE mapea `credential-id` a `labels`; AKS `User` es dynamic sin detalle de `extra`).
- No encontré doc oficial de RKE2 sobre flags por defecto del perfil CIS relacionados con auditoría/SA.

## 9. Cronología de versiones (beta/GA) y deprecaciones relevantes 1.29–1.37

### Takeaway
Todo lo necesario para "credencial por desarrollador con revocación y atribución" es GA desde v1.32/1.33 (JTI, node binding, credential-id X.509/JWT, structured authz) y v1.34 (structured authn, anonymous endpoints); 1.35–1.37 añaden constrained impersonation (beta 1.36), Pod certificates/ClusterTrustBundle (GA 1.37) y API server → webhook auth (alpha 1.37), sin nuevas deprecaciones de mecanismos de credenciales de usuario.

### Inferences
- Diseño recomendado para la app (mixto EKS/GKE/AKS/self-managed): (1) un ServiceAccount por desarrollador con RBAC segmentado, (2) un Secret ancla por credencial y token TokenRequest bound al Secret con `--duration` decidido por la app, (3) revocación = borrar el Secret (o el SA), (4) audit por `JTI` (y `issued-credential-id` en la emisión), (5) opcionalmente un exec plugin propio que renueve tokens cortos contra la app. En self-managed se puede añadir un webhook/OIDC estructurado para identidades "humanas" con `extra` propio, y en cualquier entorno un gateway con impersonation si se quiere que el audit muestre nombre de persona.
- X.509 debe descartarse como credencial de desarrollador en entornos mixtos (no revocable y no emitible en EKS); si se usa en self-managed/GKE, sólo con vidas ≤ horas.

### Gaps
- Techos de `expirationSeconds` en EKS/GKE/AKS (no documentados): verificar empíricamente.
- AKS + CSR `kube-apiserver-client`: sin fuente oficial.
- Representación de `user.extra`/`impersonatedUser` en CloudWatch/Cloud Logging/AKSAudit: no verificada en detalle.
- No verifiqué si EKS access policies y Azure RBAC for Kubernetes soportan el verbo `impersonate` (necesario para el patrón gateway en esos clústeres).
