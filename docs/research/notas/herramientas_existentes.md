# Herramientas existentes para acceso Kubernetes por desarrollador con RBAC, inventario de credenciales y auditoría (estado a 24 de septiembre de 2026)

Nota de método: las fechas de release, el estado "archived" y las licencias se han verificado contra la API pública de GitHub (`api.github.com/repos/...`) cuando ha sido posible, porque los resúmenes de páginas web daban años contradictorios en varios casos (Paralus, Devtron, Pomerium, dex). Cuando un dato sale sólo de un agregador de precios o de un resumen de búsqueda, se indica. Reddit no es rastreable por el buscador disponible, por lo que las quejas de comunidad proceden de GitHub issues, Hacker News y blogs.

## ¿Qué hacen, cómo se despliegan y en qué estado están las herramientas open source?

### Takeaway
El campo open source se divide en (a) proxies de identidad para kubectl que sí producen auditoría por request pero no inventario de credenciales (Paralus, Teleport CE, Octelium, Tailscale/NetBird API-server proxy, Pomerium, OpenUnison/kube-oidc-proxy), (b) plataformas de gestión pesadas que traen RBAC y kubeconfigs proxied como función secundaria (Rancher, Portainer BE, vCluster Platform, Devtron, APL) y (c) piezas de autenticación pura sin auditoría propia (Pinniped, dex+kubelogin, Keycloak). Tres proyectos relevantes están archivados o dormidos: jetstack/kube-oidc-proxy (archivado 17-may-2024), Kubernetes Dashboard (archivado 21-ene-2026) e Infra (sin release desde ene-2023).

#### Notas por herramienta (open source)

**Paralus**
- Qué hace: "All-in-one Kubernetes access manager. User-level credentials, RBAC, SSO, audit logs"; aceptado en CNCF Sandbox el 14-dic-2022 — [GitHub paralus/paralus](https://github.com/paralus/paralus); [CNCF](https://www.cncf.io/projects/paralus/). Fue creado por Rafay Systems — [Rafay blog](https://rafay.co/ai-and-cloud-native-blog/paralus-applies-to-become-a-cncf-sandbox-project).
- Arquitectura: el core expone las APIs de organizaciones/proyectos/clusters/roles, autentica con Ory Kratos, autoriza con Casbin y su servicio "Sentry" genera kubeconfigs únicos y autentica peticiones kubectl; el Relay Server es un "KubeAPI proxy" que valida certificados de cliente con la CA de Paralus y "forwards only authenticated and authorized kubectl requests to the cluster"; el Relay Agent se despliega en cada cluster y habla gRPC con Sentry; Dashboard y "Prompt" (kubectl web con autocompletado) completan el conjunto — [Core Components](https://www.paralus.io/docs/architecture/core-components).
- Licencia y estado: Apache-2.0, 1.213 stars, no archivado, `pushed_at` 2026-06-16, 65 issues abiertas — [GitHub API](https://api.github.com/repos/paralus/paralus). Última release v0.3.0 publicada 2026-01-16 — [GitHub API releases/latest](https://api.github.com/repos/paralus/paralus/releases/latest); la anterior v0.2.9 fue el 23-may-2024 y v0.2.8 el 14-jun-2023 — [Releases](https://github.com/paralus/paralus/releases).
- Credenciales: `pctl kubeconfig download --cluster <name>`; la CLI se configura con API key y API secret descargados del dashboard — [CLI docs](https://www.paralus.io/docs/usage/cli). El README promete "Dynamic and immediate changing and revoking of permissions" y "Automatic logging of all user actions performed for audit and compliance purposes" — [GitHub](https://github.com/paralus/paralus).
- Multi-cluster: funciona "with different clouds (EKS, AKS, etc.), and on-premises data centers operating behind firewalls" — [Docs](https://www.paralus.io/docs/).
- CI: "just-in-time service account creation" y acceso para "CI/CD tools" — [InfraCloud](https://www.infracloud.io/blogs/zero-trust-security-kubernetes-access-paralus/).
- Coste: gratis.

**Pinniped**
- Qué hace: Supervisor es un servidor OIDC que federa con un IdP externo y emite tokens propios; Concierge intercambia esa credencial por otra que el cluster entiende "or by an impersonation proxy" — [Install Concierge](https://pinniped.dev/docs/howto/install-concierge/).
- Estado: Apache-2.0, 739 stars, `pushed_at` 2026-09-23 — [GitHub API](https://api.github.com/repos/vmware/pinniped); releases v0.47.0 (8-jul-2026, modo FIPS y reintentos GitHub IdP), v0.46.0 (11-may-2026), v0.45.0 (30-mar-2026) — [Releases](https://github.com/vmware/pinniped/releases).
- Auditoría: registra eventos de autenticación (TokenCredentialRequest, endpoints OAuth2/OIDC) en los pod logs con `"auditEvent":true`; no registra los requests de API del usuario, "that's handled by standard Kubernetes audit logging" — [Audit logging](https://pinniped.dev/docs/reference/audit-logging/).
- Clusters soportados: TKG, kind, kubeadm, EKS, GKE y AKS; la estrategia TokenCredentialRequest sólo en clusters self-hosted, los managed requieren el impersonation proxy, que por defecto necesita un Service LoadBalancer — [Supported clusters](https://pinniped.dev/docs/reference/supported-clusters/).
- CI: se recomienda un usuario no humano en el IdP con `PINNIPED_USERNAME`/`PINNIPED_PASSWORD`, y para OIDC hay que habilitar `allowPasswordGrant` — [CI/CD howto](https://pinniped.dev/docs/howto/cicd/); la petición original de login no interactivo es la issue #686 — [Issue 686](https://github.com/vmware/pinniped/issues/686).

**Teleport Community Edition**
- Licencia: código AGPLv3 desde 1-dic-2023 — [Blog AGPL](https://goteleport.com/blog/teleport-oss-switches-to-agpl-v3/); desde Teleport 16 (junio 2024) los binarios/imágenes pasan a licencia comercial de Community Edition, libre para individuos y para empresas con "<100 employees and less than $10MM in annual recurring revenue" — [Blog licencia](https://goteleport.com/blog/teleport-community-license/); la feature matrix confirma "Free usage for companies with <100 employees and <US$10M annual revenue" — [Feature matrix](https://goteleport.com/docs/feature-matrix/).
- Limitaciones CE: SSO sólo GitHub (OIDC/SAML son Enterprise), sin Device Trust ni hardware keys, access requests sólo por CLI; session recording, export de audit a SIEM y Machine ID están en todas las ediciones — [Feature matrix](https://goteleport.com/docs/feature-matrix/).
- Arquitectura K8s: Proxy + Auth + "Teleport Kubernetes Service" como agente; registro manual por kubeconfig, por IAM join o auto-discovery — [Kubernetes access intro](https://goteleport.com/docs/enroll-resources/kubernetes-access/introduction/).
- Auditoría: evento `kube.request` (T3009I) con user, login, verb, kubernetes_cluster, namespace, resource_kind, resource_name, request_path, response_code; además kube.create/update/delete — [Audit events](https://goteleport.com/docs/reference/audit-events/kubernetes-access/).
- CI: Machine ID (`tbot`) genera un `kubeconfig.yaml` que se renueva automáticamente — [Machine ID K8s](https://goteleport.com/docs/machine-workload-identity/access-guides/kubernetes/).
- Última release v18.10.0 el 9-jul-2026 — [GitHub API](https://api.github.com/repos/gravitational/teleport/releases/latest).

**Rancher**
- Apache-2.0, 25,9k stars — [GitHub](https://github.com/rancher/rancher); v2.15.2 publicada 2026-09-23, que corrige CVE-2026-88805 "logout didn't revoke public API session tokens, leaving them valid until natural expiry" — [GitHub API](https://api.github.com/repos/rancher/rancher/releases/latest).
- kubeconfig: el contexto por defecto pasa por el Rancher server como proxy de autenticación; el "authorized cluster endpoint" directo sólo existe en RKE2/K3s, no en EKS/GKE/AKS importados — [Use kubectl and kubeconfig](https://ranchermanager.docs.rancher.com/how-to-guides/new-user-guides/manage-clusters/access-clusters/use-kubectl-and-kubeconfig).
- Tokens: `kubeconfig-default-token-ttl-minutes` = 43200 (30 días) y `auth-token-max-ttl-minutes` = 129600 (90 días) desde v2.8; para CI se crean API keys con TTL ajustado — [API tokens](https://ranchermanager.docs.rancher.com/reference-guides/about-the-api/api-tokens).
- Auditoría: el API audit log escribe "all requests to the Rancher API and all responses"; niveles 0 (metadata) a 3 (response body); campos auditID, user (name, group, extra con principal, token ID), method, requestURI, responseCode, remoteAddr — [Enable API audit log](https://ranchermanager.docs.rancher.com/how-to-guides/advanced-user-guides/enable-api-audit-log); la doc no dice explícitamente si los requests kubectl proxied por `/k8s/clusters/...` se incluyen — [SUSE doc](https://documentation.suse.com/cloudnative/rancher-manager/latest/en/observability/logging/enable-api-audit-log.html).

### Inferences
- Sólo Paralus, Teleport, Octelium y el proxy de Tailscale (beta) producen de serie un registro por request atribuible a la persona; Pinniped, dex/kubelogin, Keycloak, Headlamp y rbac-manager dependen del audit log nativo de cada API server, que en clusters managed hay que activar y pagar aparte.
- Ninguna herramienta open source revisada expone un "inventario de credenciales vivas" como objeto de primera clase (quién tiene qué kubeconfig/token, cuándo caduca, cuándo se usó por última vez). Rancher y Portainer tienen listado de tokens por usuario, pero acoplado a plataformas grandes; Paralus tiene la CA y puede revocar, pero la documentación pública no describe un inventario consultable.
- Las herramientas que usan impersonation con una única service account de proxy (Tailscale, NetBird, Pomerium, OpenUnison, kube-oidc-proxy) funcionan igual en EKS/GKE/AKS que en self-managed porque no tocan flags del API server; las que dependen de OIDC en el API server (dex/Keycloak directo, Pinniped TokenCredentialRequest, Pomerium JWT) sólo cubren self-managed.
- Compatibilidad kubectl/k9s/Helm/Lens: todas las que emiten un kubeconfig estándar con exec plugin o token (Teleport tsh, Pomerium-cli, Tailscale configure kubeconfig, NetBird write-kubeconfig, Paralus pctl, Rancher, Portainer, OpenUnison) son transparentes para cualquier cliente que lea kubeconfig; sólo Twingate lo afirma explícitamente en su documentación (ver sección comercial).

### Gaps
- No se pudo confirmar en la documentación de Rancher si el API audit log incluye los requests kubectl proxied por `/k8s/clusters/...`; un resumen automático afirmó que no, pero el texto citado sólo muestra ejemplos de `/v3/...` y `/v1/...`.
- No se verificó la release exacta de OpenUnison (un resumen de búsqueda menciona 1.0.44 el 19-feb-2026 sin URL primaria); sí consta actividad en el repo hasta 23-sep-2026.
- No se localizó documentación de Paralus sobre expiración/rotación de certificados de usuario ni sobre HA del relay; la página de arquitectura sólo enumera componentes.
- No se comprobó la compatibilidad específica de Lens/FreeLens con los exec plugins de Pinniped, Paralus o Teleport (no hay fuentes primarias en esta búsqueda).
- El CNCF landscape no pudo consultarse (página renderizada en JavaScript), así que la lista de "newcomers" se basa en búsquedas: Octelium (2025), hoop.dev, Border0 (absorbido por Tailscale), Apono/Britive (comerciales).

## ¿Qué ofrecen las herramientas comerciales y cuánto cuestan?

### Takeaway
Las comerciales (Teleport Enterprise, StrongDM/Delinea, Rafay, Palette, ACM, GKE Enterprise, Akeyless, Boundary Enterprise, Okta OPA, Entra, Tailscale, Twingate) resuelven auditoría por request e identidad propagada al cluster, pero con precios por usuario/recurso que para equipos pequeños empiezan en decenas de miles de dólares al año (Teleport mediana 50.950 $/año; StrongDM 25-60 k$ para 10-25 usuarios) o con funciones de Kubernetes reservadas al tier Enterprise (Twingate, vCluster Platform, Tailscale PAM extensions).

## ¿Qué dan las opciones nativas de EKS, GKE y AKS para "una credencial por desarrollador con auditoría", y qué se pierde en un entorno mixto?

### Takeaway
Cada cloud resuelve identidad y auditoría sólo para sus propios clusters: EKS con access entries + IAM y audit logs en CloudWatch (con atribución débil para roles asumidos), GKE con IAM/Workforce Identity Federation (Identity Service for GKE deprecado desde 1-jul-2026) y AKS con Entra ID authorization; ninguno emite credenciales para clusters self-managed ni de otro cloud (Azure Arc excluye EKS/GKE explícitamente; EKS Connector es sólo lectura en consola), así que un entorno mixto acaba con tres inventarios de identidades y tres formatos de audit log.

### Cited Findings
- EKS access entries asocian permisos K8s a una identidad IAM (p. ej. un rol asumido), vía access policies de AWS o grupos K8s, y "leveraging AWS IAM features like CloudTrail audit logging and multi-factor authentication" — [Access entries](https://docs.aws.amazon.com/eks/latest/userguide/access-entries.html).
- El username de un rol se genera como `arn:aws:sts::111122223333:assumed-role/my-role/{{SessionName}}`; AWS recomienda añadir `{{SessionName}}` para trazabilidad — [Set custom username](https://docs.aws.amazon.com/eks/latest/userguide/set-custom-username.html). El session name "is generated client side and could be forged" y el audit log de K8s no incluye el accessKeyId para correlar con CloudTrail — [aws-iam-authenticator issue 263](https://github.com/kubernetes-sigs/aws-iam-authenticator/issues/263).
- Los audit logs de EKS van a CloudWatch Logs con coste; entradas >1 MB se truncan (el request K8s puede ser 1,5 MiB); la política de auditoría registra RequestResponse para la mayoría de grupos — [EKS best practices](https://docs.aws.amazon.com/eks/latest/best-practices/auditing-and-logging.html).
- `aws eks get-token` usa una URL presignada de STS con expiración de 15 minutos que "will not be changing" — [aws-cli issue 5185](https://github.com/aws/aws-cli/issues/5185).
- EKS Connector para clusters externos: "Any external cluster information shown in the EKS console is view-only" y sólo soporta RegisterCluster/ListClusters/DescribeCluster/DeregisterCluster — [Connector grant access](https://docs.aws.amazon.com/eks/latest/userguide/connector-grant-access.html).
- GKE: "Starting on July 1, 2026, Identity Service for GKE is deprecated and is unsupported in GKE version 1.37 and later"; el reemplazo es Workforce Identity Federation, que "doesn't require any in-cluster installation" — [Use external identity providers](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/oidc). En Cloud Audit Logs el usuario federado aparece en `principalSubject` con el workforce pool y el subject externo — [Example logs WIF](https://docs.cloud.google.com/iam/docs/audit-logging/examples-workforce-identity).
- GKE Connect gateway sí alcanza attached clusters en EKS/AKS y on-prem, pero los requests kubectl se auditan en cada cluster, no en Cloud Audit Logs — [Gateway audit logging](https://docs.cloud.google.com/kubernetes-engine/fleet-management/docs/connect-agent/audit-logging-gateway).
- AKS: "Assign once, govern many clusters" con asignaciones a nivel resource group/subscription; "Every role assignment change is recorded in the Azure Activity Log"; los requests individuales quedan en el audit log del cluster — [Concepts](https://learn.microsoft.com/en-us/azure/aks/concepts-cluster-authorization). Las asignaciones tardan hasta 5 minutos en propagarse y el tenant de Entra debe coincidir con el de la suscripción — [Entra ID authorization](https://learn.microsoft.com/en-us/azure/aks/entra-id-authorization).
- Azure Arc extiende Azure RBAC a clusters self-managed (kubeadm, Cluster API) pero no a EKS/GKE/OpenShift ni Arm64, exige modificar el kube-apiserver y rotar anualmente el certificado del webhook guard; kubectl usa `az connectedk8s proxy` o kubelogin con PoP tokens — [Azure RBAC on Arc](https://learn.microsoft.com/en-us/azure/azure-arc/kubernetes/azure-rbac).
- Con Entra integrado, PIM permite elevación just-in-time a grupos de acceso — [AKS PIM](https://learn.microsoft.com/en-us/azure/aks/privileged-identity-management).

### Inferences
- "Una credencial por desarrollador" en managed significa "una identidad IAM/Google/Entra por desarrollador"; el token kubectl es efímero (15 min en EKS) y no existe como objeto inventariable: el inventario real es la lista de access entries / role assignments / IAM bindings, que hay que consultar con tres APIs distintas.
- La auditoría por request existe en los tres, pero cada uno en su sink (CloudWatch, Cloud Logging, Log Analytics) con formatos y costes propios; en un entorno mixto no hay una vista única sin un proxy común o un pipeline de logs que normalice los tres.
- Para los clusters self-managed del mismo equipo, ninguna de las tres identidades cloud sirve salvo Arc (con restricciones fuertes) o GKE Connect gateway (que requiere registrar el cluster en un fleet de Google), así que la elección práctica es un proxy propio o un IdP OIDC común.

### Gaps
- No se cuantificó el coste de los audit logs en GKE (Cloud Logging) ni AKS (Log Analytics `kube-audit`) en esta búsqueda.
- No se verificó el flujo exacto de kubectl con Workforce Identity Federation (`gcloud auth login --login-config`) más allá de que se usa `gcloud container clusters get-credentials`.

## Por herramienta: ¿hay inventario de credenciales, auditoría por request, credenciales para CI y cuánto cuesta operarla?

### Takeaway
Auditoría por request atribuible a una persona la dan de serie Teleport, StrongDM, Paralus, Octelium, Rafay, Tailscale (beta) y Twingate; inventario explícito de credenciales emitidas sólo existe, y de forma acoplada, en Rancher/Portainer (tokens por usuario), Teleport (certificados y Machine ID "Service Discovery: live inventory") y las consolas cloud (access entries/role assignments); la carga operativa va desde un único proxy stateless (kube-oidc-proxy, Tailscale/NetBird proxy) hasta plataformas con base de datos, CA y varios servicios (Paralus con PostgreSQL+Kratos, Teleport con Auth/Proxy/agentes, Rancher, StrongDM gateways).

### Cited Findings

|---|---|---|---|---|
| Paralus | CA propia y kubeconfigs por usuario (no consta vista de inventario) | Sí, en relay | SA JIT y API keys | Core + Kratos + Casbin + Sentry + Relay Server + Relay Agent + Dashboard + Prompt — [Core components](https://www.paralus.io/docs/architecture/core-components) |

| Teleport | Usuarios/roles; Machine ID "Service Discovery: Live inventory of machine and workload identities" — [Pricing guide](https://goteleport.com/api/files/teleport-pricing-guide.pdf) | kube.request — [Audit events](https://goteleport.com/docs/reference/audit-events/kubernetes-access/) | Machine ID tbot — [Docs](https://goteleport.com/docs/machine-workload-identity/access-guides/kubernetes/) | Proxy + Auth + Kubernetes Service — [Intro](https://goteleport.com/docs/enroll-resources/kubernetes-access/introduction/) |

### Inferences
- El "inventario" que la mayoría ofrece es de identidades y roles, no de credenciales materializadas: en los diseños de certificados efímeros (Teleport, Pinniped, EKS) la credencial dura minutos/horas y el inventario útil es "quién puede pedir una", mientras que en los de tokens largos (Rancher 30-90 días, Portainer configurable, SA tokens compartidos en hoop.dev/Boundary) el inventario de tokens vivos es un riesgo real y ninguna herramienta lo expone como lista con "último uso".
- Las herramientas de red (Tailscale, NetBird, Twingate, Cloudflare) son las más baratas de operar (un pod en cluster) pero su auditoría de Kubernetes es reciente, beta o de pago.

### Gaps
- Rafay, Okta OPA y Akeyless no documentan públicamente un listado de credenciales activas por usuario.
- No se encontró para Paralus documentación de HA ni de dependencias exactas (PostgreSQL, Elasticsearch) más allá del listado de componentes.

## ¿Qué tendría que hacer mejor o distinto una app ligera propia para justificarse frente a adoptar?

### Takeaway
Una app propia sólo se justifica si cubre a la vez cuatro cosas que ninguna herramienta gratuita y ligera junta hoy: (1) inventario explícito de credenciales emitidas por persona y por pipeline con caducidad, revocación y último uso; (2) auditoría por request con la identidad de la persona en todos los clusters, managed y self-managed, sin depender del audit log de cada cloud; (3) credenciales para CI de primera clase; y (4) un único proxy stateless desplegable dentro o fuera del cluster, con kubeconfig estándar, sin CA propia ni base de datos pesada.

### Cited Findings
- Estado de las alternativas gratuitas cercanas: Paralus da proxy+audit pero necesita Kratos, Casbin, Sentry, Relay Server/Agent, Dashboard y Prompt — [Core components](https://www.paralus.io/docs/architecture/core-components), con una release al año (v0.2.9 23-may-2024, v0.3.0 16-ene-2026) — [Releases](https://github.com/paralus/paralus/releases), [API](https://api.github.com/repos/paralus/paralus/releases/latest); Pinniped no audita requests — [Audit](https://pinniped.dev/docs/reference/audit-logging/); Teleport CE limita SSO a GitHub y el uso a <100 empleados — [Feature matrix](https://goteleport.com/docs/feature-matrix/); Tailscale audita en beta y fail-open y el proxy debe vivir in-cluster — [Docs](https://tailscale.com/docs/features/kubernetes-operator/how-to/session-recording), [Issue 15230](https://github.com/tailscale/tailscale/issues/15230); Octelium audita por request pero es una plataforma ZTNA completa bajo AGPL-3.0 — [API](https://api.github.com/repos/octelium/octelium), [Docs](https://octelium.com/docs/octelium/latest/management/core/service/kubernetes).
- Mecanismo probado y portable: impersonation con un service account de proxy funciona en managed y self-managed (Tailscale, NetBird, OpenUnison, kube-oidc-proxy, StrongDM Identity Alias) — [KB 1437](https://tailscale.com/kb/1437/kubernetes-operator-api-server-proxy), [NetBird](https://docs.netbird.io/use-cases/kubernetes/api-server-proxy), [OpenUnison](https://openunison.github.io/deployauth/), [StrongDM](https://docs.strongdm.com/admin/resources/clusters/kubernetes-identity-alias/); el audit nativo registra "both the real and impersonated identity" — [Kubernetes authorization](https://kubernetes.io/docs/reference/access-authn-authz/authorization/).
- Detalle a superar en SPDY: exec/cp/port-forward requieren soporte de protocolo en el proxy (OpenUnison recurre a kube-oidc-proxy) — [OpenUnison](https://openunison.github.io/deployauth/); Akeyless lo trata como opción aparte — [Akeyless](https://docs.akeyless.io/docs/sra-k8s-cluster).
- Auditoría de referencia a igualar: campos de Teleport kube.request (user, verb, cluster, namespace, resource_kind, resource_name, request_path, response_code) — [Audit events](https://goteleport.com/docs/reference/audit-events/kubernetes-access/) y de StrongDM (Request URI, Impersonation User/Groups, Authorization Decision) — [sdm audit](https://docs.strongdm.com/references/cli/audit/kubernetes); Tailscale registra verb, resource, HTTP details, user agent e identidad — [Docs](https://tailscale.com/docs/features/kubernetes-operator/how-to/session-recording).
- UX a respetar: kubeconfig estándar con exec plugin o token para que kubectl, Helm, k9s y Lens funcionen sin cambios — [Twingate kubeconfig sync](https://www.twingate.com/docs/kubernetes-kubeconfig-sync), [Pomerium exec plugin](https://www.pomerium.com/docs/capabilities/kubernetes-access), [kubelogin](https://github.com/int128/kubelogin).
- CI: los patrones existentes son certificados renovados por bot (Teleport tbot) — [Machine ID](https://goteleport.com/docs/machine-workload-identity/access-guides/kubernetes/), tokens SA de Vault con TTL (Boundary) — [Tutorial](https://developer.hashicorp.com/boundary/tutorials/kubernetes-connect/kubernetes-getting-started-intro), usuario no humano con password grant (Pinniped, desaconsejado) — [CI/CD](https://pinniped.dev/docs/howto/cicd/), API keys con TTL (Rancher) — [API tokens](https://ranchermanager.docs.rancher.com/reference-guides/about-the-api/api-tokens).
- Revocación: Rancher tuvo tokens que sobrevivían al logout (CVE-2026-88805) — [Release](https://api.github.com/repos/rancher/rancher/releases/latest); Portainer advierte que cambiar la expiración "will not affect previously generated kubeconfig files" — [Portainer](https://docs.portainer.io/user/kubernetes/dashboard/kubeconfig); OpenUnison invalida kubectl al cerrar la sesión web — [OpenUnison](https://openunison.github.io/deployauth/).

### Inferences
- Diferenciadores concretos que ninguna gratuita junta: (a) tabla de credenciales vivas (persona/pipeline, cluster, grupos, emitida, caduca, último uso, revocada) consultable por CLI/API; (b) revocación inmediata efectiva porque el proxy valida cada request contra esa tabla, evitando el problema de tokens largos de Rancher/Portainer; (c) un único binario proxy sin CA ni Kratos/Casbin, desplegable fuera del cluster (lo que Tailscale aún no ofrece) y fail-closed en auditoría; (d) el mismo modelo para humanos y CI, con tokens de CI de corta vida y renovables sin password grant; (e) audit log unificado por request con la identidad real, exportable, para EKS+GKE+AKS+self-managed, sin depender de CloudWatch/Cloud Logging/Log Analytics.
- Lo que no compensa construir: SSO/IdP (delegar a OIDC existente como hacen todas), UI de exploración (Headlamp existe y es el sucesor oficial), gestión declarativa de RoleBindings (rbac-manager), y session recording de exec (sólo si hay requisito de compliance; Teleport/Twingate/Tailscale ya lo hacen).
- Riesgos de la opción build: asumir SPDY/WebSocket para exec y port-forward, HA del proxy (si cae, cae el acceso, como advierte Tailscale para el proxy in-cluster) y el mantenimiento a largo plazo que ha matado a Infra y kube-oidc-proxy.

### Gaps
- No hay fuentes primarias que cuantifiquen el esfuerzo de operar Paralus o Teleport CE para un equipo pequeño; la comparación de "dificultad" se apoya en los componentes documentados.
- Falta comprobar en la práctica si alguna herramienta ligera (Octelium, OpenUnison) ya ofrece una lista de credenciales con último uso; la documentación consultada no lo describe, pero no lo descarta.
