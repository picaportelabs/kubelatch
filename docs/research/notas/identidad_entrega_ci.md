# Identidad (GitHub como IdP), entrega segura de credenciales y credenciales para CI/automatización

Estado: 24 de septiembre de 2026. Contexto: web app que emite credenciales de Kubernetes a developers de un equipo pequeño (kubectl/k9s/Lens/Helm), CI probablemente GitHub Actions, se valora la simplicidad.

Convención: las citas marcadas con `†` corresponden a fuentes primarias estables (RFCs, docs oficiales) citadas de memoria y NO re-verificadas en esta sesión; el resto se ha leído directamente durante la investigación.

## 1. GitHub como IdP: OAuth App vs GitHub App, scopes, restricción a una org, teams → roles, SAML SSO, rate limits, ausencia de OIDC para usuarios, alternativas y offboarding

### Takeaway
GitHub sirve perfectamente como IdP "social" para el login de la app (web flow o device flow), pero NO es un OpenID Provider para usuarios: no emite `id_token` ni tiene discovery endpoint, así que ni kube-apiserver ni kubelogin pueden consumirlo directamente; la app debe ser quien traduzca "sesión GitHub" → "credencial de cluster". GitHub recomienda GitHub Apps sobre OAuth Apps (tokens de usuario que caducan a las 8 h, permisos fine-grained, no sujetas a la política de "third-party application access" de la org), y la comprobación de pertenencia a la org y a teams se hace con `read:org` (OAuth App) o el permiso de organización "Members" (GitHub App).

### Cited Findings

**OAuth App vs GitHub App**
- GitHub afirma explícitamente: "GitHub Apps are preferred to OAuth apps because they use fine-grained permissions, give more control over which repositories the app can access, and use short-lived tokens". Excepción: si necesitas recursos de nivel enterprise, OAuth App — [GitHub Docs: Differences between GitHub Apps and OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)
- Ambos tipos permiten identificar/autorizar usuarios: para GitHub Apps "The flow to authorize is the same as the OAuth app authorization flow" — [GitHub Docs: Differences](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)
- Tokens de OAuth App: "tokens are long-lived by default" (opcionalmente pueden configurarse para "expire after eight hours and can be renewed with a refresh token"). Installation tokens de GitHub App: "expire after a predefined amount of time (currently 1 hour)" — [GitHub Docs: Differences](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)
- User access tokens de GitHub App: "The user access token expires after eight hours" y "the refresh token expires after six months"; prefijos `ghu_` (access) y `ghr_` (refresh); "expiration of user access tokens is enabled unless you opt out"; "Once you use a refresh token, that refresh token and the old user access token will no longer work" (rotación de refresh token) — [GitHub Docs: Refreshing user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)
- Política de acceso de terceros: si la org tiene activa la "organization application policy", "any organization member can request to install an OAuth app on an organization. An organization owner must approve or deny the request". Las GitHub Apps "aren't subject to organization application policies", aunque "If a GitHub App ... requires organization permissions, the organization owner must approve the application" — [GitHub Docs: Differences](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)

**Scopes (OAuth App)**
- `read:org`: "Read-only access to organization membership, organization projects, and team membership." `read:user`: "Grants access to read a user's profile data." `user:email`: "Grants read access to a user's email addresses." `(no scope)`: "Grants read-only access to public information (including user profile info, repository info, and gists)" — [GitHub Docs: Scopes for OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)
- Los scopes se pueden pedir incrementalmente: "applications can always send users back through the flow again to get additional permission, but don't forget that users can always say no" — [GitHub Docs: Scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)
- Parámetros útiles del web flow: `allow_signup` ("Whether or not unauthenticated users will be offered an option to sign up for GitHub during the OAuth flow. The default is `true`") y `login` ("Suggests a specific account to use") — [GitHub Docs: Authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)

**Device flow en GitHub (relevante para una CLI)**
- "The device flow allows you to authorize users for a headless application, such as a CLI tool or the Git Credential Manager." Hay que activarlo: "you must first enable it in your app's settings". Endpoint `POST https://github.com/login/device/code`; `device_code` de 40 caracteres; `user_code` "8 characters with a hyphen in the middle"; `verification_uri` = `https://github.com/login/device`; `expires_in` "default is 900 seconds or 15 minutes"; polling a `POST https://github.com/login/oauth/access_token` con `grant_type=urn:ietf:params:oauth:grant-type:device_code`; errores `authorization_pending`, `slow_down`, `expired_token` — [GitHub Docs: Authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)
- El flujo genérico está definido en RFC 8628 (OAuth 2.0 Device Authorization Grant): respuesta con `device_code`, `user_code`, `verification_uri`, `verification_uri_complete` (opcional), `expires_in`, `interval` (5 s si se omite); errores `authorization_pending`, `slow_down`, `access_denied`, `expired_token` — [RFC 8628](https://datatracker.ietf.org/doc/html/rfc8628) †

**Restringir el login a una organización y leer teams**
- `GET /orgs/{org}/members/{username}`: 204 si el solicitante es miembro y el usuario es miembro; 302 si el solicitante no es miembro; 404 si el solicitante es miembro pero el usuario no. `GET /user/memberships/orgs/{org}` devuelve `state` (active/pending) y `role` (admin/member/billing_manager). `GET /user/memberships/orgs` lista todas (filtro `state`). "Members of an organization can choose to have their membership publicized or not" y los resultados dependen de si el llamante está autenticado como miembro — [GitHub REST: Organization members](https://docs.github.com/en/rest/orgs/members)
- Dex documenta el formato de grupos que se obtiene de GitHub: "Group claims are formatted as '(org):(team)'. For example if a user is part of the 'engineering' team of the 'coreos' org, the group claim would include 'coreos:engineering'", con `teamNameField` = `name` (default) | `slug` | `both` — [Dex: GitHub connector](https://dexidp.io/docs/connectors/github/)
- Endpoints de teams: `GET /user/teams` (teams del usuario autenticado, requiere `read:org`) y `GET /orgs/{org}/teams/{team_slug}/memberships/{username}` — [GitHub REST: Team members](https://docs.github.com/en/rest/teams/members) †
- Emails: con `user:email` se puede llamar a `GET /user/emails` para obtener el email primario aunque sea privado — [GitHub REST: Emails](https://docs.github.com/en/rest/users/emails) †. FusionAuth advierte del problema al no pedirlo: "GitHub users must have a public email address" para poder enlazar cuentas — [FusionAuth: GitHub IdP](https://fusionauth.io/docs/v1/tech/identity-providers/openid-connect/github)

**SAML SSO (solo GitHub Enterprise Cloud)**
- Con SSO forzado, "You must have an active SSO session each time you authorize an OAuth app or GitHub App" y hay que "reauthorize any OAuth apps or GitHub Apps that you previously authorized". La sesión SAML dura "24 hours unless specified otherwise by your IdP" — [GitHub Docs (Enterprise Cloud): About authentication with SAML SSO](https://docs.github.com/en/enterprise-cloud@latest/authentication/authenticating-with-saml-single-sign-on/about-authentication-with-saml-single-sign-on)
- API: si un token no está autorizado para SSO → "403 Forbidden" y "the `X-GitHub-SSO` header will include a URL that you can follow to authorize your token. The URL expires after one hour". En listados multi-org: "the API will not return results from the organizations that require SAML SSO and the `X-GitHub-SSO` header will indicate the ID of the organizations" (`X-GitHub-SSO: partial-results; organizations=21955855,20582480`). Y: "Access tokens created by apps are automatically authorized for SAML SSO" — [GitHub REST: Authenticating to the REST API (Enterprise Cloud)](https://docs.github.com/en/enterprise-cloud@latest/rest/authentication/authenticating-to-the-rest-api)
- PATs: "To use your token to access resources owned by an organization that uses SAML single sign-on, authorize the token" — [GitHub Docs: Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)

**Rate limits**
- OAuth Apps "have lower rate limits and do not scale": "use the user's rate limit of 5,000 requests per hour"; GitHub Apps "scale with the number of repositories and number of organization users" — [GitHub Docs: Differences](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)

**GitHub NO es un OpenID Provider para usuarios**
- "GitHub does not implement OpenID Connect to spec" y "GitHub has not implemented a well-known configuration endpoint, so you will need to disable the Discover endpoints field and specify the endpoints manually" (authorize `https://github.com/login/oauth/authorize`, token `https://github.com/login/oauth/access_token`, userinfo `https://api.github.com/user`) — [FusionAuth: Add a GitHub IdP](https://fusionauth.io/docs/v1/tech/identity-providers/openid-connect/github)
- El único emisor OIDC de GitHub es el de Actions (`https://token.actions.githubusercontent.com`), pensado para workflows, no para personas — [GitHub Docs: About security hardening with OpenID Connect](https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/about-security-hardening-with-openid-connect)
- kube-apiserver solo acepta identidades externas vía JWT/OIDC (structured authentication config o flags `--oidc-*`), webhook token authentication o certificados; no existe un "authenticator GitHub" — [Kubernetes: Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)

**Dex en medio**
- Config del GitHub connector: `orgs: [{name: my-organization}, {name: my-organization-with-teams, teams: [red-team, blue-team]}]`; `loadAllGroups`; `useLoginAsID` (username en vez de GitHub ID); `preferredEmailDomain` (soporta `*.example.com`); callback `(dex issuer)/callback` — [Dex: GitHub connector](https://dexidp.io/docs/connectors/github/)
- Pinniped Supervisor también soporta `GitHubIdentityProvider` como upstream — [Pinniped: Login](https://pinniped.dev/docs/howto/login/)

**Offboarding (webhooks y sesiones)**
- Webhook `organization` con acciones `member_added`, `member_removed`, `member_invited`, `deleted`, `renamed`; webhook `membership` (teams) con `added`/`removed`; ambos disponibles como organization webhooks o para GitHub Apps "with at least read-level access for the `Members` organization permission" — [GitHub Docs: Webhook events and payloads](https://docs.github.com/en/webhooks/webhook-events-and-payloads)
- Pinniped: el usuario es "prompted by `kubectl` to interactively authenticate once per day" — [Pinniped: Login](https://pinniped.dev/docs/howto/login/)

### Inferences
- Para una app de equipo pequeño, **GitHub App** es la opción que GitHub recomienda y encaja mejor: user access token de 8 h + refresh token de 6 meses con rotación, permiso "Members: read" para membership/teams, y recepción de webhooks `organization`/`membership` para offboarding desde la misma app. Una **OAuth App** con `read:org` + `user:email` sigue siendo válida y más simple de montar (un solo client_id/secret, sin private key ni instalación), pero está sujeta a la "third-party application access policy" de la org (un owner debe aprobarla) y sus tokens son long-lived por defecto.
- `read:user` es en la práctica prescindible: `GET /user` con cualquier token devuelve el perfil público; lo que realmente hace falta es `read:org` (membership + teams) y `user:email` (email aunque sea privado).
- Restricción a una org: tras el login, llamar a `GET /user/memberships/orgs/{org}` y exigir `state == "active"` (evita aceptar invitaciones pendientes); mapear roles con `GET /user/teams` filtrando por `organization.login`. Guardar el `id` numérico de GitHub como identidad estable, nunca solo el `login` (los usernames se pueden renombrar y reciclar, misma lógica que ha llevado a GitHub a los "immutable subject claims" en Actions).
- Con SAML SSO forzado (solo Enterprise Cloud): como los tokens creados por apps quedan "automatically authorized for SAML SSO" si había sesión SAML al autorizar, la app debe estar preparada para recibir 403 + `X-GitHub-SSO: required; url=...` cuando el usuario ya no tiene sesión SAML o fue desprovisionado, y tratarlo como "re-login necesario". Un equipo pequeño en plan Free/Team no tendrá SAML, así que es un caso a documentar pero no a optimizar.
- Rate limits: 5.000 req/h por usuario es más que suficiente para un login + 2–3 llamadas de membership por sesión; cachear el resultado de membership durante la vida del token de la app evita gastar cuota innecesariamente.
- Frecuencia de re-validación recomendada: (1) en cada emisión/renovación de credencial de cluster (que con credenciales de 8–12 h implica al menos una vez por jornada), (2) inmediatamente al recibir `organization.member_removed` o `membership.removed`, y (3) un barrido periódico (p. ej. cada hora) por si se pierde un webhook. Esto alinea la app con los ciclos que ya usan GitHub (SAML 24 h, user token 8 h) y Pinniped (login diario).
- Alternativas: Google Workspace, Entra ID y Keycloak son OpenID Providers completos (emiten `id_token`, tienen discovery), por lo que kube-apiserver (structured auth) o kubelogin podrían consumirlos directamente sin que la app emita tokens; GitHub no. **Dex** convierte GitHub en un OIDC issuer real (grupos `org:team`), lo cual permitiría kubelogin/kube-apiserver "puros"; pero para un equipo pequeño supone desplegar y operar un componente adicional (issuer público, TLS, storage, client secrets) y aun así hay que gestionar el mapeo de grupos → RBAC y el kubeconfig. Si la app ya va a existir (para RBAC y auditoría), meter Dex en medio aporta poco; tiene sentido solo si se quiere que el cluster valide tokens OIDC estándar sin depender de la app en runtime.

### Gaps
- No he verificado si los endpoints `GET /orgs/{org}/members/{username}` y `GET /user/memberships/orgs/{org}` requieren exactamente el permiso "Members" en una GitHub App (la página REST leída no lo especifica); la doc de webhooks sí lo nombra para eventos de membership.
- No he encontrado una fuente oficial que cuantifique la latencia entre la eliminación de un miembro de la org y la invalidación de las autorizaciones de OAuth/GitHub Apps para esa org.
- No hay fuente primaria que compare cuantitativamente Dex vs "app propia" para equipos pequeños; la valoración es inferencia.

## 2. Entrega y uso de credenciales por developers: kubeconfig con token, exec credential plugin + CLI, one-time links, kubectl oidc-login; cómo lo hacen kubelogin, Pinniped, Teleport, gcloud y aws eks get-token; comportamiento en k9s/Lens/Helm/ArgoCD/Terraform

### Takeaway
Toda la industria (EKS, GKE, AKS/kubelogin, Teleport, Pinniped, int128/kubelogin) ha convergido en el **client-go credential plugin (`exec`)**: el kubeconfig no contiene secretos, un binario obtiene una credencial de corta duración (8–15 min en AWS, "una vez al día" en Pinniped) y la cachea localmente. Funciona con cualquier herramienta basada en client-go (kubectl, k9s, Helm, Terraform provider), con la salvedad práctica de las apps de escritorio como Lens, que no heredan el `PATH` del shell y necesitan rutas absolutas. Un kubeconfig con bearer token embebido sigue siendo el fallback más simple y "offline", pero solo es aceptable si el token es de corta duración.

### Cited Findings

**Mecanismo `exec` de client-go**
- Campos del bloque `exec`: `command`, `args`, `env`, `apiVersion` (`client.authentication.k8s.io/v1`, también `v1beta1`), `interactiveMode`, `provideClusterInfo`, `installHint`. Respuesta `ExecCredential` con `token` o `clientCertificateData`/`clientKeyData` y `expirationTimestamp`; client-go cachea la credencial hasta ese instante y vuelve a invocar el plugin al expirar — [Kubernetes: Authenticating (client-go credential plugins)](https://kubernetes.io/docs/reference/access-authn-authz/authentication/)
- `interactiveMode` admite `Never`, `IfAvailable`, `Always` (controla si el plugin puede pedir input al usuario) — [Kubernetes: Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/#client-go-credential-plugins) †

**int128/kubelogin (`kubectl oidc-login`)**
- Es un client-go credential plugin: kubectl lo invoca, abre el navegador contra el OIDC provider, obtiene el token y lo devuelve a kubectl. Kubeconfig:
  ```yaml
  users:
    - name: oidc
      user:
        exec:
          apiVersion: client.authentication.k8s.io/v1
          command: kubectl
          args: [oidc-login, get-token, --oidc-issuer-url=ISSUER_URL, --oidc-client-id=YOUR_CLIENT_ID]
  ```
  Cache: "Kubelogin stores the token cache to the file system by default" en `~/.kube/cache/oidc-login`; si el ID token es válido se reutiliza, si caducó se refresca con el refresh token, si ambos caducan re-autentica; logout con `kubectl oidc-login clean` — [int128/kubelogin](https://github.com/int128/kubelogin)
- Requiere un **OIDC issuer real**; GitHub no lo es (ver sección 1) — [FusionAuth: GitHub IdP](https://fusionauth.io/docs/v1/tech/identity-providers/openid-connect/github)

**Pinniped CLI**
- `pinniped get kubeconfig` genera un kubeconfig con exec plugin ("The new Pinniped-compatible kubeconfig YAML will be output as stdout"). Flujo por navegador: "kubectl will open the user's web browser and direct it to the login page", y si no hay navegador ofrece una URL para completar el login en otro dispositivo. Flujo CLI (`--upstream-identity-provider-flow` = `browser_authcode` | `cli_password`, override con `PINNIPED_UPSTREAM_IDENTITY_PROVIDER_FLOW`). Cache de sesión en `$HOME/.config/pinniped/sessions.yaml` y credenciales en `credentials.yaml`; "Deleting the contents of these directories is equivalent to performing a client-side logout". Con el Supervisor, el usuario es "prompted by `kubectl` to interactively authenticate once per day" — [Pinniped: Login](https://pinniped.dev/docs/howto/login/)

**Teleport `tsh`**
- Al actualizar kubeconfigs, tsh usa modo exec plugin: en cada ejecución kubectl invoca `tsh kube credentials` para obtener credenciales TLS; los certificados son de corta duración y con TTL, y el exec plugin permite "a login prompt when certs expire" — [gravitational/teleport issue #3691](https://github.com/gravitational/teleport/issues/3691); [Teleport: tsh CLI](https://goteleport.com/docs/connect-your-client/teleport-clients/tsh/)
- `tsh` tiene flag global `--ttl` ("Minutes to live for a session") y `--auth` ("Specify the name of authentication connector to use"); `tsh kube login` "Login to a Kubernetes cluster" con `--as` para impersonation — [Teleport: tsh reference](https://goteleport.com/docs/reference/cli/tsh/)

**AWS (`aws eks get-token` / aws-iam-authenticator)**
- El token es "base64 encoded string of a signed HTTP request to the STS GetCallerIdentity Query API" con prefijo `k8s-aws-v1.`; "The token is valid for 15 minutes (the shortest value AWS permits) and can be reused multiple times"; kubeconfig con `exec` (`apiVersion: client.authentication.k8s.io/v1beta1`, `command: aws-iam-authenticator`, `args: [token, -i, CLUSTER_ID]`) — [kubernetes-sigs/aws-iam-authenticator](https://github.com/kubernetes-sigs/aws-iam-authenticator)

**GKE**
- GKE escribe kubeconfigs con `command: gke-gcloud-auth-plugin` en el bloque exec — [GKE: API server authentication](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/api-server-authentication)

**Herramientas de escritorio y otras**
- Lens: múltiples issues por "exec: executable ... not found in $PATH": "When Kubeconfig uses exec command, the binary must be available in global PATH or absolute path must be used, but Lens application can't see PATH modifications made by any shell init scripts". Soluciones: ruta absoluta en `command` o instalar el plugin desde el mismo shell que usa Lens — [lensapp/lens #878](https://github.com/lensapp/lens/issues/878); [lensapp/lens #5976 (OIDC)](https://github.com/lensapp/lens/issues/5976); [lensapp/lens #7956 (kubelogin)](https://github.com/lensapp/lens/issues/7956); [Lens Technical FAQ](https://docs.k8slens.dev/faq/technical-faq/)
- Argo CD: el cluster secret admite `bearerToken`, `tlsClientConfig` y `execProviderConfig` (`command`, `args`, `env`, `apiVersion`, `installHint`) para "external command to supply client credentials", pero "The command must be available in the Argo CD image" (EKS/GKE usan `argocd-k8s-auth`) — [Argo CD: Declarative setup, Clusters](https://argo-cd.readthedocs.io/en/stable/operator-manual/declarative-setup/)
- Terraform provider `kubernetes` soporta un bloque `exec { api_version, command, args, env }` equivalente al de kubeconfig — [Terraform Registry: kubernetes provider](https://registry.terraform.io/providers/hashicorp/kubernetes/latest/docs) †

**One-time secret links**
- Yopass: "Yopass generates a random decryption key and encrypts the secret in your browser using OpenPGP"; "The server stores the encrypted message with an expiration time. It cannot read the secret"; "Yopass creates a link whose URL fragment contains the decryption key. URL fragments are not sent to the server"; "A one-time secret is removed after its first retrieval"; backends Redis/Memcached; "Self-host your own instance when sharing sensitive information" — [jhaals/yopass](https://github.com/jhaals/yopass)
- 1Password item sharing: los enlaces caducan a los 30/14 días, 1 día, 1 hora "or after a single person views it"; en Business el admin puede forzar "Links expire after the item is viewed one time"; se puede restringir a emails concretos con código de verificación — [1Password Support: Share items](https://support.1password.com/share-items/); [1Password: Manage item sharing](https://support.1password.com/manage-item-sharing/)

### Inferences
- **Opción (1) kubeconfig con bearer token embebido**: la más simple y la única que funciona "offline" y en cualquier GUI sin configuración; el riesgo es que `~/.kube/config` es texto plano y sobrevive a un robo de portátil. Solo es razonable con tokens de corta duración (horas) o revocables al instante desde la app; un token long-lived en kubeconfig equivale a una contraseña sin caducidad.
- **Opción (2) exec plugin + CLI propia**: el patrón estándar del sector. Para esta app, la CLI haría un login GitHub por **device flow** (activado en la GitHub App/OAuth App) o abriendo el navegador contra la propia web app, cachearía la sesión (como kubelogin en `~/.kube/cache/...` o Pinniped en `~/.config/pinniped/`) y pediría a la app una credencial de cluster corta devolviendo `ExecCredential` con `expirationTimestamp`. Ventajas: sin secretos persistentes en kubeconfig, revocación efectiva al expirar, funciona igual con kubectl, k9s, Helm y Terraform. Coste: distribuir un binario (brew/scoop/GitHub Releases) y documentar la ruta absoluta para Lens. Nota: la caché local del plugin también es un secreto en disco; la mitigación real es la duración corta, no el mecanismo.
- **Opción (3) one-time links**: útiles solo como canal de entrega inicial (p. ej. un kubeconfig de emergencia o el token de un bot) cuando no hay CLI; no sustituyen a la renovación. Si se usan, autoalojar Yopass (o similar) y compartir el enlace por un canal distinto del que lleva la contraseña/2FA.
- **Opción (4) kubectl oidc-login**: solo aplicable si hay un OIDC issuer real (Dex, Keycloak, Google, Entra) y el cluster valida OIDC directamente; con GitHub "a pelo" no es viable.
- Comportamiento por herramienta: kubectl, k9s, Helm y el provider de Terraform comparten client-go y leen el mismo kubeconfig, así que exec funciona en todos (Lens, con PATH absoluto). Argo CD es un caso distinto: corre en el cluster, no en el portátil; su forma natural de credencial es un `bearerToken`/service account del cluster destino o `execProviderConfig` con un binario dentro de la imagen, es decir, credencial de "bot", no de developer (ver sección 4).
- Preferencia de equipos pequeños: sin datos de encuesta, la evidencia indirecta es que todos los proveedores gestionados obligan al exec plugin (kubectl ≥1.26 en GKE, aws eks get-token, kubelogin en AKS) y que los devs ya conviven con él; el compromiso pragmático para un equipo pequeño es ofrecer ambas cosas: exec plugin como vía principal y descarga de kubeconfig con token corto (p. ej. ≤12 h) como fallback para GUIs o emergencias.

### Gaps
- No he encontrado encuestas o datos cuantitativos sobre qué mecanismo prefieren los equipos pequeños; la preferencia se infiere de las decisiones de los grandes proveedores.
- No he verificado el TTL por defecto ni el máximo de `tsh login` (la referencia CLI leída no lo documenta) ni la duración exacta de los tokens de `gke-gcloud-auth-plugin` (la página de GKE leída solo muestra el `command`).
- No he verificado con fuente directa el comportamiento de k9s ante exec plugins (se asume idéntico a kubectl por usar client-go); los reportes de PATH encontrados se refieren a Lens/Freelens/Radar.
- Helm: no he verificado documentación específica; la afirmación de que usa client-go/kubeconfig es conocimiento general.

## 3. Diseño de tokens: opacos hasheados (SHA-256 vs argon2) vs JWT; prefijos y secret scanning; expiración y renovación; DPoP/mTLS

### Takeaway
Para tokens generados por servidor con ≥128–256 bits de entropía, guardar un hash **SHA-256** (no argon2/bcrypt) es la práctica aceptada y la que permite verificar en cada request sin penalizar la latencia; añadir **prefijo identificable + checksum CRC32** (patrón GitHub `ghp_`) hace que los tokens sean detectables por secret scanning. JWTs solo compensan si el cluster va a validarlos sin llamar a la app (structured auth config); en ese caso hay que gestionar claves, `jti`, `exp` cortos y una lista de revocación. DPoP/mTLS no merecen la pena para un equipo pequeño: la duración corta ya acota el daño del robo.

### Cited Findings
- Formato GitHub: prefijos `ghp_` (PAT), `gho_` (OAuth), `ghu_` (user-to-server), `ghs_` (server-to-server), `ghr_` (refresh); "An underscore is not a Base64 character which helps ensure that our tokens cannot be accidentally duplicated by randomly generated strings like SHAs"; "With this prefix alone, we anticipate the false positive rate for secret scanning will be down to 0.5%"; checksum CRC32 de 32 bits en los últimos 6 caracteres: "A checksum virtually eliminates false positives for secret scanning offline. We can check the token input matches the checksum and eliminate fake tokens without having to hit our database"; entropía de OAuth tokens subió de 160 a 178 bits con 30 caracteres aleatorios — [GitHub Blog: Behind GitHub's new authentication token formats](https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/)
- Secret scanning partner program: requisitos = regex del formato, endpoint público que reciba los hallazgos, verificar firma "ECDSA-NIST-P256V1-SHA256", revocar y notificar al usuario, cuenta de pruebas; el diseño recomendado es "A uniquely defined prefix", "High entropy random strings" y "A 32-bit checksum"; el alta se hace por email a secret-scanning@github.com (no hay autoservicio) — [GitHub Docs: Secret scanning partner program](https://docs.github.com/en/code-security/secret-scanning/secret-scanning-partner-program)
- Hashing de API keys: "A fast hash like SHA-256 is secure for API keys because the primary defense is the key's high entropy, not the algorithm's speed"; bcrypt/Argon2 "are a performance anti-pattern for high-entropy secrets; reserve them for passwords", porque la autenticación por API key es stateless y se verifica en cada request — [apikeys.guide: Hashing & Storage](https://apikeys.guide/docs/security/hashing-and-storage); [Zuplo: How to implement API key authentication](https://zuplo.com/learning-center/how-to-implement-api-key-authentication); [cybersierra: Why bcrypt will kill your API performance](https://www.cybersierra.co/blog/bcrypt-performance-issues-api)
- Matiz: "SHA-256 is acceptable for a high-entropy key, but nothing guarantees that a created key is high entropy - a short or human-chosen key is offline-bruteforceable straight against the ApiKey.keyHash column if the database leaks" — [OphirPay issue #701](https://github.com/OphirPay/OphirPay/issues/701)
- OWASP Session Management: un session ID debe tener al menos 64 bits de entropía y 128 bits de longitud, generado con un CSPRNG — [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) †
- Bearer tokens (RFC 6750): quien posee el token puede usarlo; el RFC exige TLS y recomienda tokens de vida corta — [RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750) †. `jti` como identificador único de JWT para prevenir replay/revocar — [RFC 7519 §4.1.7](https://datatracker.ietf.org/doc/html/rfc7519#section-4.1.7) †
- DPoP (RFC 9449): liga access/refresh tokens a un par de claves del cliente mediante un JWT de prueba (`htm`, `htu`, `iat`, `jti`, opcional `ath`) enviado en la cabecera `DPoP`; el AS marca el token con `cnf.jkt`; nonce opcional del servidor; "DPoP provides a general defense in depth against the impact of unanticipated token leakage". Coste: el cliente genera una prueba por request, el servidor valida firmas y controla `jti` para evitar replay, y los nonces añaden round-trips. Frente a mTLS (RFC 8705) opera en capa de aplicación, viable donde los certificados de cliente son impracticables — [RFC 9449](https://datatracker.ietf.org/doc/html/rfc9449)
- Vida de tokens en productos de referencia: GitHub user access token 8 h / refresh 6 meses con rotación — [GitHub Docs: Refreshing user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens); AWS EKS token 15 min — [aws-iam-authenticator](https://github.com/kubernetes-sigs/aws-iam-authenticator); GitHub PAT: "we highly recommend adding an expiration"; "GitHub automatically removes personal access tokens that haven't been used in a year"; fine-grained PAT hasta 366 días — [GitHub Docs: Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)
- Doppler service tokens: prefijo `dp.st.`, "Copy the Service Token as it is only shown once", tokens efímeros con `--max-age` ("Once the duration is reached, the token is automatically deleted"), "Revoking a Service Token is non-reversible and immediately prevents secrets access" — [Doppler Docs: Service Tokens](https://docs.doppler.com/docs/service-tokens)

### Inferences
- Diseño recomendado para la app: token opaco = `<prefijo>_<30–40 chars base62 de CSPRNG (≥178 bits)><6 chars CRC32>`, p. ej. prefijo distintivo tipo `klt_` (developer) / `klb_` (bot); almacenar `SHA-256(token)` + `prefix` visible (primeros ~8 chars) para identificarlo en UI/logs, `expires_at`, `last_used_at`, `revoked_at`, `subject` (GitHub user id o CI subject), `scopes/rol`. Lookup por hash (índice único), comparación en tiempo constante. Un HMAC con clave del servidor (`HMAC-SHA256(server_key, token)`) en vez de SHA-256 plano añade protección si la BD se filtra sin la clave, con coste nulo.
- JWT vs opaco: si el cluster valida tokens vía la app (webhook TokenReview) o la app actúa como proxy, el token opaco es superior (revocación instantánea, sin claves). Si se quiere que kube-apiserver valide sin llamar a la app (structured auth config, ver sección 4), la app tendría que emitir JWTs firmados y publicar JWKS; entonces conviene `exp` ≤ 1 h, `jti` registrado, rotación de claves con `kid`, y aceptar que la revocación es "esperar a que caduque" salvo que se añada una denylist consultada por webhook. Para un equipo pequeño, opaco + verificación en la app es lo más simple y auditable.
- Secret scanning: el programa de partners exige un endpoint público de revocación y contacto por email; para una app interna no compensa darse de alta, pero sí copiar el formato (prefijo + checksum) para poder detectar fugas con `gitleaks`/custom patterns de GitHub Advanced Security si la org los tiene, y para que el propio backend rechace tokens malformados sin tocar la BD.
- Expiración y renovación: tokens de developer ≤ 8–12 h emitidos por la CLI/exec plugin (renovación transparente mientras la sesión GitHub siga válida y la membership se re-valide); tokens de bot con `max-age` explícito y rotación programada; refresh tokens con rotación (invalidar el anterior al usarlo, como hace GitHub). Todo token debe ser revocable por el usuario y por un admin y quedar registrado en auditoría (`created`, `used`, `revoked`).
- DPoP/mTLS: no compensan. DPoP requiere que kubectl/k9s/Helm firmen una prueba por request, cosa que client-go no soporta; mTLS ligaría el token a un certificado que habría que emitir y renovar. Para un equipo pequeño, la combinación "corta duración + revocación instantánea + auditoría de `last_used_at`/IP" es el punto óptimo.

### Gaps
- No he encontrado documentación de GitHub sobre cómo almacena sus tokens (hash) en el backend; la guía SHA-256 procede de fuentes secundarias (apikeys.guide, Zuplo) y de la práctica general, no de un estándar.

## 4. Credenciales para CI/automatización: bot tokens vs OIDC federation (GitHub Actions, GitLab CI), y cómo lo consumen Vault JWT, AWS AssumeRoleWithWebIdentity y Kubernetes Structured Authentication Configuration

### Takeaway
El patrón recomendado en 2026 es **federación OIDC**: el job de GitHub Actions pide un JWT firmado por `https://token.actions.githubusercontent.com` (`permissions: id-token: write`), lo envía a la app, la app valida `iss`/`aud`/`sub`/`exp` contra el JWKS y devuelve una credencial de cluster corta ligada a repo/ref/environment. Desde el 15 de julio de 2026 el `sub` de los repos nuevos incluye IDs inmutables (`repo:octocat@123456/my-repo@456789:ref:...`), así que las reglas de confianza deben escribirse contra `repository_id`/`repository_owner_id` o el nuevo formato. Los bot tokens long-lived solo deberían quedar para sistemas que no puedan federar (p. ej. Argo CD dentro del cluster), con expiración y rotación explícitas.

### Cited Findings
- Issuer `https://token.actions.githubusercontent.com`; claims incluidos: `sub` (p. ej. `repo:octo-org/octo-repo:environment:prod`), `aud` (por defecto la URL del owner, p. ej. `https://github.com/octo-org`; personalizable), `repository`, `repository_owner`, `ref`, `environment`, `job_workflow_ref` (`octo-org/octo-automation/.github/workflows/oidc.yml@refs/heads/main`), `runner_environment`, `actor`, `repository_visibility`, `event_name`; formatos de `sub`: `repo:ORG/REPO:environment:NAME`, `repo:ORG/REPO:ref:refs/heads/main`, pull_request; el workflow necesita `id-token: write`; se obtiene con `getIDToken()` del toolkit o `curl` usando `ACTIONS_ID_TOKEN_REQUEST_URL`/`ACTIONS_ID_TOKEN_REQUEST_TOKEN`; el token es de corta duración y "valid only for a single job"; los admins pueden exponer custom properties como claims `repo_property_*`; validación recomendada en el proveedor: `iss`, `aud`, `sub`, expiración — [GitHub Docs: About security hardening with OpenID Connect](https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/about-security-hardening-with-openid-connect)
- Immutable subject claims: nuevo formato `repo:octocat@123456/my-repo@456789:ref:refs/heads/main`; se aplica automáticamente desde el **15 de julio de 2026** a repos nuevos y a repos renombrados/transferidos, con opt-in para los existentes; motivo: "If a repository or organization name was recycled, a new owner could mint tokens with the same subject claim, potentially gaining unauthorized access to cloud resources"; el delimitador es `@` (corrección del 10 de junio de 2026); hay un endpoint de API para previsualizar el `sub`; no aplica a GHES — [GitHub Changelog (2026-04-23): Immutable subject claims for GitHub Actions OIDC tokens](https://github.blog/changelog/2026-04-23-immutable-subject-claims-for-github-actions-oidc-tokens/)
- Impacto real: usuarios de `aws-actions/configure-aws-credentials` reportaron que trust policies escritas contra el `sub` antiguo fallan para repos nuevos desde esa fecha — [aws-actions/configure-aws-credentials issue #1888](https://github.com/aws-actions/configure-aws-credentials/issues/1888); [GitHub Docs: Configuring OpenID Connect in AWS](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/configuring-openid-connect-in-amazon-web-services)
- Vault JWT auth: config con `oidc_discovery_url` | `jwks_url` | `jwt_validation_pubkeys` y `bound_issuer`; roles con `role_type: jwt`, `bound_audiences` ("must **exactly** match at least one of the `aud` claims declared for the JWT"), `bound_subject`, `bound_claims` (mapa de claims exigidos; `bound_claims_type: glob` permite patrones), `user_claim`, `claim_mappings`, `groups_claim`, `token_ttl`, `token_policies`; login `vault write auth/jwt/login role=demo jwt=...` — [Vault Docs: JWT/OIDC auth method](https://developer.hashicorp.com/vault/docs/auth/jwt)
- Kubernetes Structured Authentication Configuration (`AuthenticationConfiguration`, `--authentication-config`): promovida a **GA/stable en v1.34** (KEP-3331); soporta múltiples JWT authenticators concurrentes, validación con expresiones CEL, recarga dinámica del fichero sin reiniciar el apiserver; campos `issuer.url`, `audiences`, `discoveryURL`, `claimMappings` (`username`, `groups`, `uid`, `extra`), `claimValidationRules`, `userValidationRules` — [Kubernetes v1.34 release blog](https://kubernetes.io/blog/2025/08/27/kubernetes-v1-34-release); [kubernetes/enhancements #3331](https://github.com/kubernetes/enhancements/issues/3331); [Kubernetes: Authenticating](https://kubernetes.io/docs/reference/access-authn-authz/authentication/); [Microsoft Open Source Blog: JWT it like it's hot](https://opensource.microsoft.com/blog/2025/05/08/jwt-it-like-its-hot-a-practical-guide-for-kubernetes-structured-authentication/)
- GitLab CI: los jobs pueden declarar `id_tokens:` con `aud` y reciben JWTs firmados por la instancia de GitLab (issuer = URL de la instancia) con claims como `project_path`, `namespace_path`, `ref`, `ref_type`, `environment` — [GitLab Docs: ID token authentication](https://docs.gitlab.com/ci/secrets/id_token_authentication/) †
- AWS: `AssumeRoleWithWebIdentity` intercambia un OIDC token de un proveedor registrado en IAM por credenciales temporales de STS, sujeto a la trust policy del rol (condiciones sobre `aud`/`sub`) — [AWS STS API: AssumeRoleWithWebIdentity](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRoleWithWebIdentity.html) †
- Argo CD (bot dentro del cluster): acepta `bearerToken` o `execProviderConfig` cuyo binario debe estar en la imagen — [Argo CD: Declarative setup](https://argo-cd.readthedocs.io/en/stable/operator-manual/declarative-setup/)
- Doppler documenta el mismo enfoque para bots: tokens efímeros con `--max-age`, revocación inmediata e irreversible — [Doppler Docs: Service Tokens](https://docs.doppler.com/docs/service-tokens)

### Inferences
- **Patrón recomendado para la app (simple)**: endpoint `POST /v1/ci/token` que recibe el JWT de Actions (cabecera `Authorization: Bearer <id_token>`), lo valida con el JWKS de `https://token.actions.githubusercontent.com/.well-known/openid-configuration` (cachear claves), exige `aud` = un valor propio de la app (p. ej. `https://kubelatch.example.com`, pidiendo el token con `audience=`), comprueba `exp`/`nbf`, y busca una "trust rule" configurada por un admin: `repository_owner_id` + `repository_id` (o el `sub` con IDs inmutables) + opcionalmente `ref`/`environment`/`job_workflow_ref` (para reusable workflows). Si hay match, emite un token de cluster opaco con TTL ≈ duración máxima del job (p. ej. 1 h, ampliable) asociado a un ServiceAccount/RBAC de bot y registra `repository`, `run_id`, `actor` y `sub` en auditoría. Esto replica lo que hacen Vault (`bound_claims`) y AWS (trust policy) sin desplegar ninguno de los dos.
- Escribir las reglas contra `repository_id`/`repository_owner_id` (claims numéricos) o el nuevo `sub` con `@id` evita que un rename o un repo reciclado hereden confianza; y como el cambio de GitHub solo afecta a repos nuevos/renombrados, la app debe aceptar ambos formatos de `sub` durante la transición.
- Alternativa "sin app en el camino": configurar `AuthenticationConfiguration` en kube-apiserver con un JWT authenticator para `token.actions.githubusercontent.com` (username = `claims.sub`, `claimValidationRules` en CEL sobre `repository_id`/`ref`) y hacer que el job use el id_token directamente como bearer contra el apiserver. Es elegante, pero requiere control del apiserver (no siempre posible en managed K8s), cuidado con que el `aud` sea único por cluster, y pierde la auditoría/revocación centralizada de la app. Para este proyecto tiene más sentido que la app siga siendo el punto de emisión.
- Bot tokens long-lived: reservar para Argo CD u otros controladores in-cluster que no puedan hacer el intercambio OIDC en cada uso, con expiración obligatoria (p. ej. 90 días), prefijo distinto (`klb_`), owner identificado, rotación documentada y alerta cuando `last_used_at` supere N días.
- GitLab CI: mismo patrón con otro issuer (la URL de la instancia GitLab) y claims `project_path`/`namespace_id`; la app puede modelar "issuers de confianza" como configuración, sin código específico por proveedor.

- La documentación de GitHub no indica la vida exacta (`exp`) del id_token de Actions; solo que es de corta duración y por job.
- No he verificado en esta sesión la doc de GitLab ni la de AWS STS (citas †).
- No he encontrado fuentes que documenten cómo debe comportarse una app receptora frente a `job_workflow_ref` cuando se usan reusable workflows en organizaciones distintas; la recomendación de incluirlo en la trust rule es inferencia.

## 5. UX de entrega segura: "show once, copy, download kubeconfig" en productos de referencia (GitHub PAT, AWS access keys, Doppler, 1Password, Infisical) y one-time links

### Takeaway
El estándar de facto es: mostrar el secreto una sola vez inmediatamente tras crearlo, con botón de copiar y opción de descargar un fichero (kubeconfig/.csv), advertir de que no podrá verse de nuevo, exigir expiración por defecto, y ofrecer "regenerar" y "revocar" en lugar de "ver". Para entrega a terceros o sin CLI, un one-time link cifrado en cliente (Yopass, 1Password "one-time view") es el mecanismo aceptado.

### Cited Findings
- GitHub PAT: se elige expiración al crear ("Infinite lifetimes are allowed" salvo política de org), "To provide additional security, we highly recommend adding an expiration to your personal access tokens", "Treat your access tokens like passwords", "GitHub automatically removes personal access tokens that haven't been used in a year", y hay que copiar el token al portapapeles en el momento de la creación — [GitHub Docs: Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)
- Doppler: "Copy the Service Token as it is only shown once"; revocación irreversible e inmediata; tokens efímeros — [Doppler Docs: Service Tokens](https://docs.doppler.com/docs/service-tokens)
- AWS IAM access keys: la consola muestra la secret access key solo en el momento de la creación, con opción de descargar un `.csv`; después no puede recuperarse, solo desactivar/eliminar y crear otra — [AWS IAM User Guide: Managing access keys](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_access-keys.html) †
- 1Password: enlaces de compartición con caducidad (30/14 días, 1 día, 1 hora) o "after a single person views it"; política de Business "Links expire after the item is viewed one time"; posibilidad de restringir a destinatarios verificados por email — [1Password Support: Share items](https://support.1password.com/share-items/); [1Password Support: Manage item sharing](https://support.1password.com/manage-item-sharing/); [1Password Community: One-time view items](https://www.1password.community/discussions/1password/sharing-one-time-view-items-the-recipient-can-save-it-forever/24115)
- Yopass: cifrado en navegador, clave en el fragmento de URL que "are not sent to the server", borrado tras la primera lectura, expiración configurable, recomendación de autoalojar — [jhaals/yopass](https://github.com/jhaals/yopass)
- GitHub secret-scanning: un token con prefijo + checksum es detectable si acaba en un commit, lo que justifica diseñar el formato aunque no se participe en el partner program — [GitHub Docs: Secret scanning partner program](https://docs.github.com/en/code-security/secret-scanning/secret-scanning-partner-program)

### Inferences
- Flujo recomendado para la web app: (1) el usuario elige nombre, rol/cluster y expiración (con máximo por política, por defecto corto); (2) la app muestra el token **una sola vez** en una pantalla dedicada con botón "Copy", botón "Download kubeconfig" (fichero generado en servidor con el token embebido, `Content-Disposition: attachment`, nunca cacheado) y un aviso explícito "no podrás volver a verlo"; (3) en el listado posterior solo aparecen prefijo visible, fecha de creación, expiración, `last_used_at` y acciones "Revoke"/"Regenerate"; (4) el kubeconfig descargado puede incluir además el bloque `exec` apuntando a la CLI, de modo que si el dev instala la CLI deje de depender del token embebido. Registrar en auditoría la descarga (quién, cuándo, IP) sin registrar el token.
- Para Lens y otras GUIs, el "download kubeconfig" es el camino más simple; para el resto, la CLI con device flow evita por completo la pantalla de "show once".
- Un one-time link (Yopass autoalojado) es adecuado para entregar credenciales de bot a un tercero o a alguien sin acceso aún a la app; no debería ser el canal habitual entre la app y sus propios usuarios, que ya están autenticados.

## 6. Compliance básico: inmutabilidad del audit trail, retención y GDPR al registrar identidad de developers e IPs

### Takeaway
Un audit log de emisión/uso/revocación de credenciales es tratamiento legítimo bajo GDPR (interés legítimo/obligación de seguridad), pero las IPs y los identificadores de GitHub son datos personales: hay que documentar la base legal, fijar retención finita (habitualmente 12–18 meses para registros de seguridad) y minimizar. Para que el log sea evidencia, "append-only" no basta: hace falta encadenado de hashes (y, opcionalmente, anclaje externo o WORM) para que sea tamper-evident.

### Cited Findings
- Las direcciones IP son datos personales bajo GDPR (incluidas las dinámicas, según jurisprudencia del TJUE) — [OptimizeSmart: GDPR IP address logging](https://optimizesmart.com/blog/gdpr-ip-address-logging-retention-and-monitoring/); [TermsFeed: GDPR and log data](https://www.termsfeed.com/blog/gdpr-log-data/)
- Base legal habitual para logs de acceso/seguridad: interés legítimo u obligación legal; conviene registrarla y fijar una ventana proporcional al fin, "typically 6–12 months"; la práctica común es 30–90 días para logs operativos y 12–18 meses para registros de seguridad/auditoría, documentado y revisado anualmente; GDPR no fija plazos pero exige que no se conserven indefinidamente y que exista borrado automático — [Last9: GDPR log management](https://last9.io/blog/gdpr-log-management/); [Databunker: GDPR-compliant logging](https://databunker.org/use-case/gdpr-compliant-logging/); [UK MoJ security guidance: Logging and monitoring](https://security-guidance.service.justice.gov.uk/logging-and-monitoring)
- Los audit logs se consideran tratamiento legítimo y necesario cuando sirven a "security monitoring, fraud detection, compliance and accountability, and legal and regulatory obligations" — [Databunker: GDPR-compliant logging](https://databunker.org/use-case/gdpr-compliant-logging/)
- Inmutabilidad: los auditores reconocen tres patrones para no-repudio: almacenamiento append-only (solo INSERT), hash chains criptográficas (cada registro incluye el hash del anterior) y WORM (S3 Object Lock, Azure Immutable Blob); "Append-only is not tamper-evident—you need hash chaining to prove nothing in the past has changed"; para detectar reescrituras privilegiadas de toda la tabla se puede anclar la cabeza de la cadena en un medio externo append-only — [Velt: How to add an audit trail to a SaaS product (May 2026)](https://velt.dev/blog/how-to-add-audit-trail-to-saas-product); [Tracehold: Immutable audit log with HMAC hash chaining](https://tracehold.ai/blog/immutable-audit-log-hmac-hash-chain/); [dev.to: Tamper-evident audit log for SOC 2 / ISO 27001](https://dev.to/gentlyding/how-we-built-a-tamper-evident-audit-log-for-soc-2-and-iso-27001-evidence-jl4)
- Referencia general de buenas prácticas de logging (qué registrar, qué no, protección de logs) — [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) †

### Inferences
- Para la app: tabla `audit_events` solo-inserción (sin permisos UPDATE/DELETE para el rol de la app), cada fila con `prev_hash` y `hash = SHA-256(prev_hash || contenido canónico)` (o HMAC con clave fuera de la BD), y un job periódico que verifique la cadena y publique la cabeza en un destino externo (bucket con Object Lock, o simplemente un fichero firmado fuera del host). Eventos mínimos: login GitHub (user id, org check result), emisión de token (sujeto, rol, expiración, prefijo), uso (`last_used_at` agregado, no cada request si el volumen lo desaconseja), revocación, cambios de RBAC/trust rules, intercambio OIDC de CI (repo id, run id, sub).
- GDPR: registrar `github_user_id` + `login` + IP + user agent es proporcionado para seguridad; documentar interés legítimo, retención (p. ej. 12 meses para auditoría de credenciales, 90 días para logs técnicos), borrado automático, y un procedimiento para atender derechos de acceso/supresión (la supresión puede limitarse por la necesidad de conservar la evidencia de seguridad; dejar constancia del criterio). Nunca registrar el token ni su hash completo en logs, solo el prefijo visible.

- No he localizado en esta sesión una fuente primaria (EDPB/ICO/AEPD) que fije una retención concreta para logs de seguridad; los rangos 6–18 meses proceden de guías secundarias.
- No se ha investigado el marco NIS2/ISO 27001 en detalle (fuera del alcance "brief").
